# Security and deployment posture

These are deliberate, accepted decisions — not open bugs. Read them before "fixing" the corresponding behavior. Each one is a trade-off that was chosen knowingly for a self-hosted, single-database deployment; a change that "corrects" one of them needs a subsystem-level decision, not a drive-by patch.

- **Authorization is workspace-scoped (single tenant).** There is no per-instance or per-database ownership: every authenticated `workspaceMember` can read all instances, databases, metadata, lineage and OpenLineage data (the read baseline in `backend/store/predefined_roles.go`); writes require `workspaceAdmin` or an explicit `permission` annotation. Introducing per-resource IAM would be a subsystem-level change.
- **`allUsers` is server-managed and carries the member baseline only.** It matches every authenticated principal, including everyone who registers later, so `CheckAllUsersBinding` (`backend/store/policy.go`) accepts it only on the `roles/workspaceMember` binding and rejects it on any other role, a full replace is refused when it drops that binding, and every writer of the policy runs that check rather than only the IAM RPC. The IAM page never offers the member and renders that one row read-only, re-adding it to an editable draft so a policy that lost it can be repaired. Granting every member more than the read baseline therefore takes an explicit decision — changing the baseline in `backend/store/predefined_roles.go`, or binding another role to a group an identity provider keeps populating; custom roles are granted to named users and groups. The "at least one active admin" guard follows the same principle: a binding counts only while its condition holds, and one of the counting bindings must be unconditional, so no single write leaves the workspace unmanageable.
- **Stored credentials are encrypted, and whether database read access is enough to recover them is the deployment's choice.** Every instance and data source credential (`password`, `ssl_ca`, `ssl_cert`, `ssl_key`, `ssh_password`, `ssh_private_key`) and every LLM provider API key **in the instance and LLM profile rows** is persisted as a `v1:`-prefixed AES-256-GCM value — a fresh 12-byte nonce, the ciphertext and a 16-byte tag (`backend/common/crypto`) — so equal plaintexts no longer produce equal ciphertexts, and a value that fails to authenticate is an error naming the field and the instance, never garbage that the next write would store as the new plaintext. The data key is 32 random bytes generated on first startup into the `ENCRYPTION_KEY` setting; `AUTH_SECRET` now signs JWTs only, so the retired scheme's worst property is gone with it — one readable `instance.metadata` row is no longer a 32-byte known-plaintext window onto both every credential and the JWT signing key. Setting `METAXISDATA_ENCRYPTION_KEY` wraps that data key with the GCM cipher of a key kept outside the database: a leaked table, a dump or a backup is then not enough to decrypt anything, and the process says so in one startup line. Leaving it unset keeps the deployment zero-config and is the accepted trade-off — the data key lives in the same database, so read access to the whole database still recovers every credential, exactly as the retired obfuscation's did; it is only the partial leaks, the determinism, the known-plaintext recovery and the shared key that are gone. A key-encryption key configured after the fact wraps the existing data key on the next startup, and a rotation is the new key in `METAXISDATA_ENCRYPTION_KEY` plus the retired one in `METAXISDATA_ENCRYPTION_KEY_PREVIOUS`: the data key is re-wrapped, no credential is re-encrypted, and the previous variable is only ever used to open a wrapped key. A previous key is only ever used to open a wrapped data key, never to wrap one, so retiring a key cannot quietly promote it back. Losing the key-encryption key with no previous entry, or editing `ENCRYPTION_KEY` by hand, makes the credentials unreadable; the server refuses to start rather than serving garbage, and they must be entered again. A **missing** `ENCRYPTION_KEY` is one of those cases rather than a fresh start: a key is minted only when the setting is absent, and a database that kept credentials but lost the row fails startup instead of running on a new key that can read none of them. A key that parses but does not belong to this deployment — edited by hand, or restored from another one — fails startup for the same reason: before the resolved key is installed, and before a configured key-encryption key would re-wrap it, it has to open a credential the database already holds. With no stored credential there is nothing to prove, and a fresh install simply has none. The failure names the remedy, because a lost key cannot be recovered from the database: restore the `ENCRYPTION_KEY` setting (or the key-encryption key that opens it), or clear the affected credentials and enter them again. An unreadable credential is then the running server's per-row failure, which reports the field and the instance instead of skipping it. Nothing is migrated from the retired obfuscation, and the field rename is what a leftover row now looks like: its credential sits under the old JSONB key (`obfuscatedPassword`, `apiKeyEncrypted`), which the new schema does not know, so the tolerant unmarshaler drops it and the credential reads back **empty** — with no error — and the next write of that row drops the old key for good. A database that may hold such rows therefore needs its credentials re-entered rather than an error to rely on; the project has not been deployed, so no deployment carries one. The audit ledger is the one place a credential-shaped field still reaches a database in the clear: its redaction misses `ssl_ca` (L5 in `docs/security-review-2026-10.md`). What the key buys is also only about *reading* a database: an attacker who can write to it is outside this bullet, and can still point an LLM profile's `base_url` somewhere of their choosing and have the server fetch from it with the decrypted key (see the outbound-policy item in `docs/security-review-2026-10.md`).
- **The CLI stores its credential in clear text.** `mxd` writes the bearer token it received from a device login to `~/.config/metaxisdata/config.json` (mode 0600) or to `$METAXISDATA_CONFIG`. The token is equivalent to a seven day session, and the CLI never prints it; hiding it from a local file was not worth a keychain dependency. The server address is saved beside it, because a token is issued by one server and remembering it next to another address would fail every later request.
- **`mxd` talks to one server, and the token only goes there.** The HTTP client refuses a redirect that leaves the address `--server` names — a subdomain of it included, which `net/http` counts as the same domain, and a downgrade from https to http on the same host — instead of following it, and it keeps the standard library's ten-redirect cap, which installing a redirect policy of its own would otherwise drop. The token layer independently attaches the `Authorization` header only to that host. The standard library's own protection is not enough here: it drops the header only when a redirect leaves the server's *domain*, while this client re-attaches it on every hop because that header is what exempts the CLI from the cookie-based CSRF protection. Failing the request rather than following it anonymously is deliberate — the CLI serves one server, so a redirect off it is a misconfiguration or an attack, and the error names both hosts. The device login's confirmation address comes from the server too, so the browser opener accepts only an `http`/`https` URL with a host (`javascript:` and `file:` are refused before the program that opens them is started), and on Windows it is `rundll32 url.dll,FileProtocolHandler` rather than `cmd /c start`, whose command line would turn a `&` in a server-supplied URL into a second command. The address itself is still printed as the server named it, so a server can name any page for the person to look at; keeping control characters out of that output is the separate CLI output-hardening item.
- **Analysis scopes live only in the process environment.** `mxd` reads `METAXISDATA_SCOPES` per invocation and never writes it anywhere. Several agents share a machine while serving different projects, and any remembered scope set would be silently overwritten by whichever agent ran last. Which scopes a project uses is a per-project decision the user keeps in their own project docs.
- **Device login state is process-local.** `backend/component/state` holds the pending requests, so a client's create, approve and exchange must reach the same replica: run one replica, or put sticky routing in front. Approving reuses the approver's web session and does not re-evaluate the password policy — that policy only governs password sign-in, and applying it here would lock SSO-only users out of the CLI over a random password they never chose.
- **gRPC reflection is anonymous.** The reflection handlers are registered without the authentication interceptor, so the registered service/message definitions are public; `/grpc.reflection` is deliberately absent from the authentication exemption list (`backend/api/auth/config.go`).
- **Destructive schema sync is log-only.** When a synced snapshot no longer contains an object, the runner deletes it and records the GUIDs in `logSchemaSyncDeletion` (`backend/runner/schemasync/syncer.go`). There is deliberately no shrink threshold or confirmation flag: a MySQL `information_schema` only lists objects the connecting user may see, so a privilege change can empty a snapshot. Treat the deletion log as the only trace. A database row's `deleted` flag follows the same rule and is **single-directional**: hiding may be triggered by any observation that the target no longer has the database (a name missing from an instance snapshot, or a per-database sync whose driver reports `common.NotFound`), while showing it again is only done by the instance enumeration (`SyncInstance` → `CreateDatabaseDefault`, when the name reappears in a snapshot). A per-database sync therefore never clears the flag; a `deleted` database is kept with its metadata as history and is revived when a snapshot lists it again.
- **An account is identified by its user ID; the email address is administrative and SSO binds to the provider's subject.** Only a caller holding `metaxisdata.users.update` can set an address — their own or anyone else's — because the address is how the member is recognized outside the workspace (`backend/api/v1/user_service.go`). An IdP login resolves against the stored `principal_idp_binding` row for its provider subject, never against the provider's email claim, so a provider-side or administrative address change keeps the same account. An existing account that carries no binding is deliberately **not** adopted by an email match: whoever created it still holds its password, and the server cannot tell an administrator's pre-provisioned row from a squatter's, so the login is refused and the address is left for an administrator to resolve by moving that account's address or deleting it — a deleted row cannot sign in and no longer holds the address, so the identity provider's user is then provisioned as a new account. Deactivating an account is likewise final until an administrator restores it — signing in through the IdP does not undelete. A workspace can opt out of the whole rule **for named identity providers** with `sso_email_identity_idps` (Settings → General, empty by default): through a listed provider an SSO login is identified by its email claim, and an existing account with that address becomes reachable — adopted, with its password replaced by a random one and every session minted before that invalidated, if it had no provider binding at all; merely added to if it already signed in through a provider, which leaves its sessions alone. Listing a provider is the operator asserting that it verifies its addresses and hands each one to a single person, because an address claim anyone can set names an account anyone can sign in as. It stays a per-workspace, per-provider decision, not an installation default. An account may be bound to several providers at once (`principal_idp_binding`), so a person enrolled in two of them signs in through either and lands in the same account.
- **SSH bastion host keys are verified per data source, not against a server-side file.** A data source that tunnels through SSH carries the trusted host key in `ssh_host_key`: one `SHA256:`/`MD5:` fingerprint or one `known_hosts`/`authorized_keys` line per entry, which is what `ssh-keyscan` prints. The connection is refused when the list is empty or the presented key is not in it, because the tunnel carries the database credentials and a host that only answers on that address could otherwise collect them. There is no switch to accept an unknown host key, and the host column of a pasted `known_hosts` line is not re-checked: the list is the configuring administrator's assertion about this data source's `ssh_host`, so paste only the line for the bastion named there. The trust anchor lives with the instance instead of in a file on the server host: whoever holds the instance write permission that sets `ssh_host` also sets the key it must present, so no operator has to log into the server to add a bastion. The SSH handshake — including the `SSH_AUTH_SOCK` fallback — and the *wait* for a channel open through an established tunnel are bounded by `util.SSHTimeout` (30s); an open that is abandoned is released when the tunnel closes, and a connection test is bounded by its own deadline and counts against the instance's `maximum_connections` like every other path that opens a driver.
- **`audit_log` and `meta_registry_resource_history` are kept forever.** `runner/maintenance` only prunes ExplainSQL cache rows, old LLM debug logs and OpenLineage runs (per `openlineage_retention_days`); the audit ledger and the metadata history are never pruned. Retention is paired with a write bound rather than with deletion: a ConnectRPC request body is capped per handler (`backend/server/grpc_routes.go`; an oversized body is refused before the interceptor runs, so it leaves no row at all) and a row records at most 8 KiB per string and 256 KiB per request/response payload — a larger payload is replaced by a `{"truncated": …}` marker while the method, actor, resource, status and origin are kept, so the row still says what happened (`backend/component/audit/audit.go`). The ConnectRPC read baseline is not audited, so no row is written for it. The rate at which rows are written is bounded as well: the audited methods a signed-in caller may call are budgeted per principal, and a request refused by a budget is refused before the audit interceptor, so it adds no row (see the per-principal budget bullet).
- **Reverse-proxy contract.** Cookie-based writes trust `Origin`/`Sec-Fetch-Site` (`backend/server/csrf.go`) and audit records believe `X-Forwarded-For` only from peers listed in `--trusted-proxies` (`backend/api/v1/audit.go`). A deployment behind a proxy must normalize or strip those headers and list the proxy address, otherwise CSRF requests can look same-origin and audit IPs collapse to the proxy. The forwarding chain is read **from the right**: each hop appends the address it saw, so the server walks from the nearest hop outward and stops at the first address that is not a listed proxy (`backend/component/audit/audit.go`). That means the leftmost entry, the one a caller can choose, is never used while any untrusted hop remains, and a proxy that appends to `X-Forwarded-For` (the usual configuration) is enough — it does not have to sanitize the value. The same address is the rate-limit key for the anonymous endpoints, so a caller cannot reset its bucket by sending a header. A proxy on the server host is listed like any other, `127.0.0.1` included — which does mean a local process counts as a trusted peer, exactly as listing any proxy address does; the REST gateway's own loopback self-connection is recognized separately and never needs to be listed (see the bullet on `/v1/*` below). An entry that is not a parseable address is skipped rather than recorded, since it can only be caller-chosen text: a deployment that lets a proxy pass an unparseable hop through will attribute the request to the next hop inward.
- **The REST gateway's own hop never decides the client address.** `/v1/*` is answered by grpc-gateway dialing the server's own port, so the Connect handler's peer is loopback and every REST audit row would otherwise read 127.0.0.1. The `/v1/*` middleware stamps the outer request's peer into `Grpc-Metadata-Metaxisdata-Client-Peer`, after deleting any caller-supplied copy, together with `Grpc-Metadata-Metaxisdata-Gateway-Proof` — an HMAC of that address under a random secret generated inside the process and never disclosed (`backend/component/audit/audit.go`). `audit.ClientAddress` substitutes the stamped peer for a loopback peer only when the proof verifies, so a caller that reaches the Connect handler directly — including through a same-host proxy that forwards unknown headers — cannot forge it, and one that reaches the gateway has both headers overwritten. Loopback therefore need not be listed in `--trusted-proxies` for the gateway's sake; a same-host reverse proxy in front of `/v1/*` is listed for its own hop like any other.
- **A revoked access token stays revoked, in the database.** `Logout` records the token's `jti` in `revoked_token` with the token's own expiry (`backend/store/revoked_token.go`), and every entry point refuses it through the same `TokenAuthenticator.Resolve` (`backend/api/auth/authenticator.go`). The record cannot be evicted by another principal the way the previous bounded in-memory set could, and its size is bounded by the login rate limits together with the prune — a record never outlives the token it refuses. A process caches a revocation decision for at most 30 seconds, and a logout performed on a replica enters that replica's cache immediately (a table read racing the logout cannot overwrite it with a stale "live" answer), so another replica may keep accepting a token revoked there for up to that window; like device login and OAuth pending state, cross-replica behavior depends on either one replica or sticky routing. A token minted before its last password change is refused for the same reason from persisted state. Logout also deletes the credentials that could replace the token it revokes: the web session's refresh row named by its cookie, and — for an MCP token, whose `cid` claim names the registration — every grant that client holds for that user. A failure to delete them is logged rather than reported, because the access token itself is already revoked.
- **The anonymous credential endpoints are budgeted per source and globally.** `Login` and `CreateUser` each spend a bcrypt comparison or hash on an unauthenticated caller, so a ConnectRPC interceptor gives each a fixed-window budget keyed by the resolved client address with a global backstop (`backend/api/v1/throttle_interceptor.go`; 120/min and 300/min for Login, 20/min and 100/min for CreateUser). `Refresh` shares the Login budget: it is the other anonymous entry point that spends a database round trip on caller-supplied input, and the budget is loose enough that several tabs renewing at once are unaffected. `CreateSSOState` has a budget of its own with the same numbers (120/min and 300/min): it spends no CPU, but each call writes one nonce into the cache that in-flight SSO flows occupy, and a login cannot reach the identity provider without a state this server issued — so the budget is also what bounds the outbound calls to a provider. That cache holds up to 4096 nonces, deliberately more than the global budget can admit while a nonce is still usable — the window is fixed, so the ceiling is `ceil(TTL/window) + 1` full quotas rather than `TTL/window` (6 × 300 = 1800 for the shipped values) — so the budget bounds the cache itself and not merely the request rate: filling it would evict the state of users who are mid-sign-in, which is the failure the endpoint's callers see as "invalid or expired state". The cache does not expire entries on a timer (`lru.New`, not `NewWithExpire`): a nonce leaves it when it is redeemed or evicted, and the TTL is checked at redemption, so what protects a valid nonce is the capacity above the budget and not the TTL. The per-source Login budget is loose on purpose — a whole office behind one NAT address is normal use — so the *global* budget is what actually bounds the deployment's bcrypt work. `CreateUser` exempts a signed-in caller, because an administrator may create users in bulk and bounding an authenticated principal is the general per-user rate-limit work rather than this ceiling; `Login` does not, since it is not a normal signed-in call and every request still spends bcrypt on whoever the address names. Requests refused by the budget are answered before the audit interceptor runs, so they leave no ledger row. `Logout` carries a budget of its own (120/min and 300/min) rather than spending Login's: it is anonymous and audited, and a token this server signed can be replayed against it — revoking the same token twice writes the same no-op revocation but a fresh ledger row every time. Failed logins are counted in two independent dimensions (`backend/component/state/login_limiter.go`): ten failures lock the account for five minutes whatever sources they came from — including refusing the correct password, so a stranger can lock an account for one window — and twenty failures lock the source across every account it tries. A successful login clears the account's counter but deliberately not the source's, so one known password cannot buy a fresh spraying budget from a shared address. All of these counters are process-local, like every other one in `backend/component/state`.
- **A signed-in caller's ledger writes are budgeted per principal, and the refusal is the backpressure.** Every authenticated method that writes a permanent `audit_log` row — plus `ExplainSQL`, which drives the LLM agent loop, and `FetchLLMModels`, which calls the provider — carries a fixed-window budget keyed by `(principal, method)` with one deployment-wide counter across all of them (3000/min and 30000/min; `backend/api/v1/principal_throttle_interceptor.go`). The set is read from each method's `audit` annotation, so a method that gains one is covered without editing the interceptor; `ListAuditLogs` is the one deliberate exemption, because it only reads. The interceptor runs before the audit interceptor, so a request it refuses never runs and leaves no row: the ledger still records every action that happened, and a caller that loops a ledger-writing method is told to slow down rather than the record being dropped. The LLM calls it covers were previously unbounded in cost as well as in rows. Like the anonymous budgets these counters are process-local, and they are deliberately loose — a bulk import is thousands of rows but not thousands of calls a minute — so they bound a loop rather than pace ordinary work.
- **MCP tokens are bound to the MCP resource, and to nothing else.** The OAuth access token the MCP endpoint accepts carries the canonical `<external_url>/mcp` as its `aud` (`backend/api/auth/mcp_token.go`), so a web or CLI session token is refused at `/mcp` and an MCP token is refused on the ConnectRPC API. It also carries a `cid` claim naming the registration it was issued to, which is what lets `Logout` retire that client's refresh tokens; a web, CLI or API token carries no `cid` and so cannot touch any grant. Changing `external_url` therefore invalidates outstanding MCP tokens, which is correct — the resource they were minted for no longer exists at that identifier — and the client authorizes again; the stored grants are pinned to the same resource, so they are refused too rather than minting a token for the old identifier.
- **The MCP surface is off by default and needs `external_url`.** `mcp_enabled` (Settings → General) gates the endpoint, the protected-resource metadata, the authorization-server metadata and every `/oauth/*` route; all of them answer 404 while it is off, so a disabled deployment advertises nothing. Enabling it requires a configured `external_url`, because the issuer and the resource identifier are derived from it and are never taken from the request's `Host`: a request-derived audience would drift with the caller and would make an issuer mix-up possible. `external_url` is already readable without credentials (`GetWorkspaceProfileSetting` is anonymous for the sign-in page's benefit), so the switch's state is not a new disclosure.
- **The MCP authorization server is self-contained, and issues rotating refresh tokens.** Registration is open (RFC 7591, public clients only), but a token requires a signed-in user's explicit approval on `/oauth/consent`, and that approval is what the audit ledger records. The token exchange returns an access token and an opaque refresh token; only the refresh token's SHA-256 digest is stored, the row is deleted atomically as it is claimed (so a token is single-use and two concurrent refreshes leave exactly one working), and the grant is pinned to the `<external_url>/mcp` the user consented to, so moving the deployment invalidates it rather than re-minting for a resource that no longer exists. A grant lives 30 days and is re-checked against persisted account state on every rotation — the principal must still exist and not be deactivated, and the grant must not predate the last password change — so revocation does not depend on the access token's remaining lifetime. `Logout` deletes the grants of the client the presented token names, and the maintenance runner prunes expired rows. This is deliberate: an MCP client that loses its access token no longer needs a browser round trip, at the cost of a persisted credential that outlives a session. No `jwks_uri` is published: the signing key is the deployment's symmetric `AUTH_SECRET` and the only verifier is the same process. Pending authorization requests and authorization codes still live in process memory like device logins, so an approval and its completion must reach the same replica; refresh tokens do not, so a refresh may reach any replica.
- **A web session has its own rotating refresh token, in the database.** A `web` login sets two HttpOnly cookies: the seven-day access token and a refresh token with a 30-day absolute lifetime. `AuthService.Refresh` consumes the refresh cookie (`DELETE … RETURNING`, so rotation is single-use), re-reads the principal — a deactivated account or one whose password changed after the session was established is refused — and sets a new pair; the rotated token inherits the original issue time and deadline, so refreshing cannot extend a session indefinitely, and the login rate budget also bounds this anonymous endpoint. `Logout` deletes the row the cookie stands for and clears both cookies. Like the MCP flow, only the digest is stored, so database read access does not hand out a usable credential.
- **Every MCP tool call is audited, reads included.** The ConnectRPC read baseline is not audited (those methods carry no `audit` annotation); the MCP surface deliberately is, one row per call, because it is a remote entry point a model drives. A call refused for lack of permission leaves a row too — being turned away is the event worth keeping — and the arguments are bounded before they are rendered (64 KiB for the argument tree, then 8 KiB per string and 256 KiB for the whole payload), because the ledger is kept forever. Those rows are permanent — `audit_log` is never pruned — and the arguments are recorded with the sensitive-field redaction; the authorization code and the access token are never part of a row.
- **The MCP endpoint is stateless, cross-origin protected, budgeted and time-bounded.** It keeps no session, so every request is authenticated on its own and nothing survives between calls, and it is wrapped in the standard library's cross-origin protection because the MCP SDK applies none by default. A rejected request answers 401 or 403 with `WWW-Authenticate: Bearer resource_metadata="<current resource metadata URL>", scope="metaxisdata.mcp.read", error=…`. Because a model drives it and every call reads the registry and writes a permanent row, a principal gets 600 calls a minute (global backstop 6000) and a request may take 60 seconds at most; a call refused by that budget is a tool failure and is audited like any other. The budget caps the call *rate*, not the row count — auditing every call, refused ones included, is the deliberate rule above. The budget is per principal rather than per address or per token, so agents behind one address do not share a ceiling. Because that per-principal budget cannot see a request that carries no or an invalid token — identity resolution refuses it first — the endpoint also counts every request against the resolved client address before the bearer check (6000/min, global backstop 60000), sized ten times the per-principal numbers so it bounds probing rather than pacing a fleet behind one address. Like every other counter in `backend/component/state` it is process-local, so replicas each hold their own window.

- **Every response carries a fixed document policy, and the SPA cannot be framed.** `backend/server/echo_routes.go` sends `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` together with `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff` on every response, so `/device` (and the OAuth consent page) can no longer be embedded and approved for a victim. The three relaxations are the least the SPA needs: Vue binds dynamic styles and monaco-editor injects a stylesheet at runtime (`style-src`), monaco ships its glyphs as `data:` images and loads a same-origin module worker. `base-uri 'none'` and `form-action 'self'` are free — there is no `<base>` and every form is submitted by script to its own origin — and keep an injected `<base>` or `<form>` from re-pointing relative URLs or posting the session elsewhere. A unit test compares the whole served directive map against the expected one, and an integration test requires the same headers from a running server on the SPA routes, the ConnectRPC paths, the REST gateway, the OAuth endpoints and `/mcp`; because the assertion reads the response rather than the constant, deleting the middleware turns it red. Inline script and eval are refused — which is why vue-i18n's catalogs are JIT-compiled (`__INTLIFY_JIT_COMPILATION__` in `frontend/vite.config.ts`); without that flag its message compiler uses `new Function` and the policy breaks every translated string rather than only the security property. No `Strict-Transport-Security` is sent: it needs a trustworthy https signal, and the middleware would trust a caller-supplied `X-Forwarded-Proto`. The Vite dev server serves the SPA itself and sends none of these headers, so a development page is outside the policy; a build with a cross-origin `VITE_API_BASE_URL` would also be blocked by `default-src 'self'`, which is fine for the single-binary deployment this is built for.
- **A link the server derives from caller-supplied data is a web address or nothing — but it may still be any web address.** The Airflow `log_url` facet is written by whoever holds an ingestion key, and it is bound to an `href`, so `DeriveAirflowLinks` keeps only an absolute `http`/`https` URL with a host and drops everything else (`backend/plugin/openlineage/airflow_links.go`). That removes script execution, not link injection: a valid `http(s)` URL to a phishing page still reaches the button, so the remaining bound is the operator's trust in whoever can ingest events. The two OpenLineage fields are re-checked in the SPA with the same whitelist (`frontend/src/utils/safeUrl.ts`), and both detail pages have a test that a `javascript:` field renders no anchor at all — the check is deliberately not a blanket rule over every `href` in the app, so a new server-supplied link needs its own gate. A `javascript:` value would otherwise run in the origin that holds the HttpOnly session cookie, where the CSRF checks pass because the request is same-origin.
- **OpenLineage ingestion bounds one event, and the pages that list OpenLineage data read stored columns rather than payloads.** The request body may be 8 MiB, so one event is capped separately at 1 MiB; its identity fields are capped at the lengths their unique btree indexes can hold (`job.namespace`/`job.name`/`run.runId` 255 bytes, job type 64, dataset namespace 255, dataset name 512), one event may name at most 1000 datasets, and the escaped run GUID is capped at 2000 bytes because per-field caps alone can approach PostgreSQL's index item size once every character needs percent-encoding (`backend/plugin/openlineage/limits.go`). A single oversized event is refused with `413`, an over-long identity with `400` — not stored and then failing its insert forever — and a batch is refused as a whole when any event in it is oversized, like an over-limit body. Ingestion also extracts what the pages show — the datasets each run read or wrote, their schema facet, the column-lineage field names and the already-whitelisted Airflow run-log URL — into `openlineage_run.airflow_run_log_url` and `openlineage_run_dataset`, whose rows cascade with their run so the retention prune keeps them in step. The run list, the task list, the dataset list/detail and the filter menus therefore never read a page's worth of `raw_payload`; `GetOpenLineageRun` still returns the payload when asked, and the run list projection omits it unless a caller opts in (`backend/store/openlineage_run.go`). Every other string an event writes into the run row — `event_type`, `producer`, `integration`, `processing_type`, the parent/root fields — is capped the same way, and an over-long Airflow link is dropped rather than stored, because the run and task lists read those columns for every row of a page and an uncapped one would let one page read an unbounded number of bytes with `raw_payload` unselected; the strings of a `columnLineage` facet are capped too, since its field names reach the indexed `column_lineage` columns. The stored schema facet (64 KiB) and column-lineage names (32 KiB) are capped at ingestion as well, and the detail's schema, job and run queries read a bounded newest-first window of references, backed by a `(namespace, name, event_time DESC)` index, so the JSONB it expands is bounded rather than proportional to the dataset's whole history. None of the dataset reads aggregates references: `openlineage_dataset` holds one row per dataset — its reference and column-lineage counts, its job counts per direction and its newest event time — and `openlineage_dataset_member` one row per (dataset, kind, value) with the number of references carrying it, both maintained by the ingest transaction and rebuilt by the retention prune, which deletes references in bulk and so cannot report which ones it took. A reference that goes away takes its member's contribution back out, which is what keeps the counts, the integrations and the sources exact under a redelivery, and one page load reads a few thousand small rows instead of grouping every reference the database holds. Four bounds come with that and are accepted: the list, its filter menus and the detail's GUID lookup all read the same window — the 5000 most recently seen datasets — so a filter searches within it and a dataset older than it is neither listed nor openable; a dataset whose events predate this schema has no extracted references and no aggregate row, so it is not listed until an event for it is ingested again (there is no backfill; the project is not deployed yet); the job count of a dataset reported under several spellings is deduplicated through its member rows rather than read from a single aggregate row; and a run deleted outside the store's retention path leaves the aggregate stale until that path reconciles it, as it leaves `openlineage_task` stale.

Two deliberate deviations from the OAuth and audit defaults, both about keeping a caller from choosing how large something is:
- A pending authorization request stores the client's fields bounded (redirect URI 2 KiB, `state` 512 bytes, code_challenge exactly 43, scope one entry), and when a request is refused for an over-long `state` the error redirect **does not echo it** — RFC 6749 §4.1.2.1 asks for the state back, but echoing a megabyte would only move it into a `Location` header. A client that packs a JWT into a state larger than 512 bytes is refused.
- A tool call's arguments are bounded at 64 KiB in the ledger before they are rendered, on top of the 8 KiB/string and 256 KiB/payload bounds. Past that the row records that arguments came, not what they were, because the endpoint accepts 2 MiB and a call refused by the budget carries its arguments too.
- **The plain-HTTP anonymous routes are rate-limited by the resolved client address, in a bounded store.** OpenLineage ingestion and the OAuth routes sit outside the ConnectRPC interceptor chain, so each carries its own limiter: one for ingestion and one per OAuth route. Ingestion is keyed by the presented ingestion key when there is one — only its SHA-256 digest is stored — and by the client address otherwise; the OAuth routes are keyed by that address alone. The address comes from `audit.ClientAddress`, the same trusted-proxy resolution the audit row and the other per-source budgets use, never from Echo's `RealIP`, which believes an `X-Forwarded-For` the caller wrote and would hand out a fresh bucket per request. That resolution is only as good as the entry list: when a trusted-proxy entry covers the client itself — `0.0.0.0/0`, or the client's own range — every hop counts as trusted and the chain falls back to its leftmost, caller-written segment, which reopens a caller-chosen bucket here exactly as it makes the audit address caller-chosen. The list must name proxies, not client ranges. Every one of these limiters uses a token-bucket store that caps the identifiers it tracks at 4096, sweeping buckets idle for three minutes and dropping an arbitrary one at capacity, in constant time, rather than hunting for the least recently seen one: a caller that invents a new identifier per request would force that hunt on every request under the mutex all the others need (`backend/server/rate_limiter.go`). That ceiling bounds the memory a caller's identifiers can cost. Each store also carries one deployment-wide bucket shared by every identifier, ten times one identifier's budget, because the identifier ceiling is only a memory bound: a caller that rotates ingestion keys still reaches a fresh per-key bucket, and the shared counter is what bounds the total work it can demand — a refused request spends nothing from either. Like every other counter here, these limiters are process-local. OpenLineage ingestion and each OAuth route are separate budgets, not one shared ceiling: sharing would tighten the anonymous OAuth surface four-fold, which is the open I2 item in `docs/security-review-2026-10.md`.
- **An MCP token can be revoked, and every anonymous OAuth route is rate-limited.** `Logout` accepts a token this server signed without requiring a particular audience (`backend/api/auth/authenticator.go`), so an MCP token has a self-service remedy and not just an expiry; provenance is what keeps the revocation cache from being flooded with forged strings. Registration, the token exchange, `/oauth/authorize` and `/oauth/authorize/complete` each carry their own per-address ceiling. A `404` from a deployment whose surface is switched off is deliberately **not** written to the ledger: nothing was registered, issued or decided, and a permanent ledger must not grow a row per probe.
- **Editing a data source's connection parameters is an administrator action, not an authorization boundary.** `extra_connection_parameters` reaches the driver's own connection syntax unchanged — MySQL-wire driver options and session variables, PostgreSQL keyword/value settings, MSSQL URL properties — and the pre-existing MySQL `allowAllFiles` blacklist checks parameter *names* only, so it does not stop a value that carries `&`/`=` from introducing another parameter (`sql_mode` set to `x&allowAllFiles=true` is accepted). It is a guard rail for an honest configuration, not a boundary. Whoever can write the field already holds the instance/data-source write permission (workspaceAdmin, or a delegated custom role) and could set `host`, `port`, `username`, `password` or `ssh_host` on the same resource, so a parameter-level whitelist would constrain the form of a decision that caller is trusted to make rather than a right they lack. The interpolated value that is *not* caller-chosen is the one that had to change: a database name a sync reads out of the target's own catalog must not be able to rewrite the connection, so the MySQL-wire DSN is rendered by `BuildDSN` (`backend/plugin/db/mysql/dsn.go`), which escapes the name with `url.PathEscape` exactly as the driver's own `Config.FormatDSN` does — a database named `x?tls=false&` stays that name instead of ending the DSN's path segment and turning the rest into driver parameters.
