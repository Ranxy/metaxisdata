# Security and deployment posture

These are deliberate, accepted decisions — not open bugs. Read them before "fixing" the corresponding behavior: each is a trade-off chosen knowingly for a self-hosted, single-database deployment, so "correcting" one needs a subsystem-level decision rather than a drive-by patch.

- **Authorization is workspace-scoped (single tenant).** Every authenticated `workspaceMember` can read all instances, databases, metadata, lineage and OpenLineage data; writes require `workspaceAdmin` or an explicit `permission` annotation. Per-resource IAM would be a subsystem-level change, so the single-tenant read baseline stays. See `.agents/docs/iam-and-permissions.md`.
- **Signup is open until an operator closes it, and the first account becomes the workspace administrator.** The first active `END_USER` is granted `roles/workspaceAdmin` in the same transaction that creates it, and self-service signup keeps working until `DisallowSignup` is set — until then anyone who reaches the port can register and, by the read baseline, read everything. Closing signup or adding a network boundary is the operator's decision, not a code default. See `.agents/docs/iam-and-permissions.md`.
- **`allUsers` is server-managed and carries the member baseline only.** It matches every authenticated principal, so it may be bound only to `roles/workspaceMember`, and a replace that drops that binding is refused; the "at least one administrator" guard requires one unconditional counting binding, so no single write leaves the workspace unmanageable. Granting every member more than the read baseline is therefore an explicit decision. See `.agents/docs/iam-and-permissions.md`.
- **Stored credentials are encrypted, and whether database read access is enough to recover them is the deployment's choice.** Credentials and LLM API keys are `v1:` AES-256-GCM values under a data key held in the `ENCRYPTION_KEY` setting; `METAXISDATA_ENCRYPTION_KEY` wraps that key with one kept outside the database. Leaving the wrapper unset is the accepted trade-off — read access to the whole database still recovers every credential. Losing or hand-editing the key makes credentials unreadable, and the server refuses to start rather than serving garbage, so they must be entered again. Rows left by the retired scheme read back **empty** with no error and are never migrated. Audit redaction misses `ssl_ca`, and an IdP `client_secret` sits in clear; anyone with database write access is outside this item. See `.agents/docs/credential-encryption.md` and `.agents/docs/security-open-items.md`.
- **The CLI stores its credential in clear text.** `mxd` saves the device-login bearer token to `~/.config/metaxisdata/config.json` or `$METAXISDATA_CONFIG` with mode 0600, beside the server address that issued it; the token is a seven-day session and is never printed. A keychain dependency was judged not worth it. See `.agents/docs/cli-mxd.md`.
- **`mxd` talks to one server, and the token only goes there.** The HTTP client refuses a redirect that leaves the address `--server` names — a subdomain included, since `net/http` counts it as the same domain, and an https-to-http downgrade on the same host — while the `Authorization` header is attached only to that host. Failing rather than following the redirect anonymously is deliberate: the CLI serves one server, so a redirect off it is a misconfiguration or an attack. See `.agents/docs/cli-mxd.md`.
- **Analysis scopes live only in the process environment.** `mxd` reads `METAXISDATA_SCOPES` per invocation and never writes it anywhere; several agents share a machine while serving different projects, and any remembered scope set would be silently overwritten by whichever ran last. Which scopes a project uses stays a per-project decision the user keeps in their own docs. See `.agents/docs/cli-mxd.md`.
- **Device login state is process-local.** Pending requests live in memory, so a client's create, approve and exchange must reach the same replica: run one replica or put sticky routing in front. Approval reuses the approver's web session and does not re-evaluate the password policy, which would otherwise lock SSO-only users out of the CLI. See `.agents/docs/cli-mxd.md`.
- **gRPC reflection is anonymous.** The registered service and message definitions are public, so the port must not be exposed to untrusted networks.
- **Destructive schema sync is log-only.** When a snapshot no longer contains an object the runner deletes it and records the GUIDs; there is deliberately no shrink threshold or confirmation flag, and a privilege change can empty a MySQL `information_schema` snapshot, so treat the deletion log as the only trace. A database row's `deleted` flag is **single-directional**: hiding follows any observation that the target no longer has the database, while only instance enumeration revives it. See `.agents/docs/schemasync.md`.
- **An account is identified by its user ID; the email address is administrative and SSO binds to the provider's subject.** An IdP login resolves against the stored binding for its provider subject, never the email claim, so an existing account without a binding is deliberately **not** adopted by an email match — the login is refused and an administrator must move or delete that account's address. A workspace can opt out **for named identity providers** with `sso_email_identity_idps` (empty by default): through a listed provider SSO login is identified by email, and an existing account with that address is taken over, its password replaced by a random one and every earlier session invalidated. Listing a provider is the operator asserting it verifies addresses for a single person, because an address claim anyone can set names an account anyone can sign in as.
- **SSH bastion host keys are verified per data source, not against a server-side file.** Each data source carries its trusted host key in `ssh_host_key`, and a connection is refused when the list is empty or the presented key is missing, because the tunnel carries the database credentials. The trust anchor lives with the instance: whoever may set `ssh_host` also sets the key it must present, so no operator logs into the server to add a bastion. Paste only the line for the bastion named there.
- **`audit_log` and `meta_registry_resource_history` are kept forever.** The maintenance runner prunes ExplainSQL cache rows, old LLM debug logs and OpenLineage runs, and removes expired tokens and refresh-token rows, but the audit ledger and the metadata history are never pruned. The distinction that matters is **rows per call, not calls**: the rate limits bound how often a method may be called, while one call can write many rows into a table the limits never look at — a schema sync writes one history row per changed object, and `BatchSyncInstances` takes up to 1000 instances per call. Retention is paired with a write bound rather than deletion, and the ConnectRPC read baseline is not audited, so it writes no row. See `.agents/docs/rate-limiting.md`.
- **Choosing a UI language writes a `User` row, and therefore a permanent audit row.** The SPA stores the BCP-47 tag it switched to in `User.language` on the caller's own profile, because server-side prose — the Explain SQL answer — is written in the language the user reads; updating your own user needs no permission, but `UpdateUser` carries the audit annotation, so the switch leaves a ledger row holding the whole request and response. The SPA writes only when the stored value actually differs, so a switch costs one row; an account whose profile carries no language is filled in from the locale the browser is already reading when the session loads, which is one more row per such account and no user choice behind it. A tag the server ships no prompt text for is refused rather than stored, and a stored tag the SPA does not ship is left alone rather than overwritten with the browser's locale. The tag rides the same untimed process-local user cache as every other user field, so another replica can keep answering in the previous language until it evicts that entry or writes that user — one replica or sticky routing, as elsewhere in this list. A write that fails leaves the interface and the answered language apart until the next switch, session load, or Explain SQL request, which settles the stored value first. See `backend/api/v1/language.go`.
- **Reverse-proxy contract.** Cookie-based writes trust `Origin`/`Sec-Fetch-Site`, and audit records believe `X-Forwarded-For` only from peers listed in `--trusted-proxies`; a deployment behind a proxy must list the proxy address, or CSRF requests can look same-origin and audit IPs collapse to the proxy. The chain is read from the right and stops at the first hop that is not a listed proxy, so the caller-chosen leftmost entry is never used and a proxy that appends is enough. See `.agents/docs/rate-limiting.md`.
- **The REST gateway's own hop never decides the client address.** `/v1/*` is answered by grpc-gateway dialing the server's own port, so the Connect handler's peer is loopback; the gateway stamps the outer request's peer with a process-local HMAC proof, substituted by the audit layer only when the proof verifies. Loopback need not be listed in `--trusted-proxies` for the gateway's sake, though a same-host proxy in front of `/v1/*` is listed for its own hop. See `.agents/docs/rate-limiting.md`.
- **A revoked access token stays revoked, in the database.** `Logout` records the token's `jti` in `revoked_token` with the token's own expiry, so every entry point refuses it and a process restart does not revive it. A replica caches the decision for at most 30 seconds, so cross-replica behavior depends on one replica or sticky routing. Logout also deletes the credentials that could replace the token: the web session's refresh row and, for an MCP token, the grants that client holds. See `.agents/docs/refresh-tokens.md`.
- **The anonymous credential endpoints are budgeted per source and globally.** `Login`, `CreateUser`, `CreateSSOState` and `CreateDeviceLogin` each carry a fixed-window budget keyed by the resolved client address with a deployment-wide backstop (Login 120/min and 300/min, CreateUser 20/min and 100/min, CreateSSOState 120/min and 300/min, CreateDeviceLogin 10/min and 100/min); `Refresh` shares the Login budget, and `Logout` has its own (120/min and 300/min). A request refused by a budget on the interceptor chain is answered before the audit interceptor runs, so it leaves no ledger row. The shared global counter is the loose-address trade-off: one exhausted ceiling blocks everyone for the rest of the window. See `.agents/docs/rate-limiting.md`.
- **A signed-in caller's ledger writes are budgeted per principal, and the refusal is the backpressure.** Every authenticated method that writes a permanent `audit_log` row — plus `ExplainSQL` and `FetchLLMModels` — carries a fixed-window budget keyed by `(principal, method)` with one deployment-wide counter across all of them (3000/min and 30000/min). The interceptor runs before the audit interceptor, so a request it refuses never runs and leaves no row: the ledger still records every action that happened, and a looping caller is told to slow down rather than the record being dropped. The counters are process-local and deliberately loose, so they bound a loop rather than pace ordinary work. See `.agents/docs/rate-limiting.md`.
  - **The counter is spent before the permission check.** The budget interceptor precedes the ACL interceptor, so a call the caller is not allowed to make still counts against it — and still leaves a row, since the audit interceptor also runs first. The budget answers how often a principal called a method, not how often it was allowed to.
  - **The deployment-wide counter is shared, so one account can spend it for everyone.** A signed-in account needs no permission at all to exhaust the 30000/min ceiling in about half a minute, after which every other principal's audited calls are refused `resource_exhausted` until the window rolls, despite fresh per-principal buckets. That availability cost is the price of bounding the ledger's total growth, and is kept deliberately.
  - **`ListAuditLogs` is exempt, and that exemption is not bounded at all.** It is the one audited method that only reads, so the "ledger write" rule does not cover it — but a refused read still writes a row, after the audit interceptor and before the ACL denial. Any signed-in account can therefore grow the permanent ledger without limit. Bounding it means treating a read that writes a row as a ledger write.
  - **A limiter's table is only pruned at its ceiling.** `WindowLimiter` drops elapsed keys only once the map is full, so a long-running process accumulates every key it has seen until then, and a full walk of the map under the limiter's mutex happens on each request past the ceiling. Keys are server-chosen and the ceiling is above what the shipped global budget can drive: it is a tail-latency boundary, not a denial of service. See `.agents/docs/rate-limiting.md`.
- **MCP tokens are bound to the MCP resource, and to nothing else.** The token the MCP endpoint accepts carries the canonical `<external_url>/mcp` as its `aud`, so a web or CLI session token is refused at `/mcp` and an MCP token is refused on the ConnectRPC API. Changing `external_url` therefore invalidates every outstanding MCP token and the stored grants pinned to it, and the client must authorize again. Details: `.agents/docs/mcp-server.md`.
- **The MCP surface is off by default and needs `external_url`.** `mcp_enabled` (Settings → General) gates the endpoint, its metadata and every `/oauth/*` route, all of which answer 404 while it is off; enabling it requires `external_url` to be configured first, because the issuer and resource identifier are derived from it and never from the request's `Host`, so an enabled surface without one cannot serve the endpoint (404/503). Details: `.agents/docs/mcp-server.md`.
- **The MCP authorization server is self-contained, and issues rotating refresh tokens.** Registration is open (RFC 7591, public clients only) with PKCE S256, but a token still needs a signed-in user's explicit approval on `/oauth/consent`; the access token lives seven days, and the server now issues an opaque rotating refresh token whose digest alone is stored and which is consumed single-use. Pending requests and codes stay process-local, so an approval and its completion must reach the same replica, while a refresh may reach any replica. Details: `.agents/docs/mcp-server.md`, `.agents/docs/refresh-tokens.md`.
- **A web session has its own rotating refresh token, in the database.** A `web` login sets a seven-day access cookie and a refresh token with a 30-day absolute lifetime; rotation is single-use and the rotated token inherits the original issue time and deadline, so refreshing cannot extend a session indefinitely, and `Logout` deletes the row it stands for. Only the digest is stored, so database read access does not hand out a usable credential. Details: `.agents/docs/refresh-tokens.md`.
- **Every MCP tool call is audited, reads included.** The ConnectRPC read baseline carries no `audit` annotation and is not recorded; the MCP surface deliberately is, one row per call, because a model drives it, and a call refused for lack of permission leaves a row too. Those rows are permanent, so arguments are redacted and bounded before they are rendered. Details: `.agents/docs/mcp-server.md`.
- **A notification stream is authenticated once, and ends itself.** `SubscribeNotifications` is scoped and authenticated like the rest of its service and deliberately not audited; authentication happens at the handshake and is not re-checked, so the server ends every stream after 30 minutes and the client's reconnect re-authenticates, which is what makes a logout or token revocation take effect inside that window. The fan-out is process-local, so with more than one replica a client must reconnect to see a message written elsewhere. Details: `.agents/docs/notifications.md`.
- **The MCP endpoint is stateless, cross-origin protected, budgeted and time-bounded.** It keeps no session, so every request is authenticated on its own, and it relies on the standard library's cross-origin protection because the MCP SDK applies none; a principal gets a per-minute call budget and a request may take 60 seconds at most, and because that budget cannot see a request with no or an invalid token, the endpoint also counts every request against the resolved client address before the bearer check. The counters are process-local. Details: `.agents/docs/mcp-server.md`.

- **Every response carries a fixed document policy, and the SPA cannot be framed.** Every response gets the same CSP together with `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`, so `/device` and the OAuth consent page can no longer be embedded and approved for a victim. No `Strict-Transport-Security` is sent, because it needs a trustworthy https signal the middleware cannot obtain, and the Vite dev server sends none of these headers, so a development page is outside the policy. The middleware is `backend/server/echo_routes.go`.
- **A link the server derives from caller-supplied data is a web address or nothing — but it may still be any web address.** The Airflow `log_url` facet is bound to an `href`, so only an absolute `http`/`https` URL with a host survives; that removes script execution, not link injection, since a valid `http(s)` URL to a phishing page still reaches the button, so the remaining bound is the operator's trust in whoever holds an ingestion key. The same whitelist is re-checked in the SPA. Details: `backend/plugin/openlineage/airflow_links.go`.
- **OpenLineage ingestion bounds one event, and the pages that list OpenLineage data read stored columns rather than payloads.** One event is capped at 1 MiB inside an 8 MiB request body, with per-field caps sized to the unique indexes that hold them, and a single oversized event is refused with `413` rather than stored and failing its insert forever. The run, task, dataset and filter pages read extracted columns and aggregate rows maintained by the ingest transaction, not a page's worth of `raw_payload`, and the permanent ledger's write rate is bounded by the interceptor budget. Details: `.agents/docs/openlineage-lineage.md`, `.agents/docs/rate-limiting.md`.

Two deliberate deviations from the OAuth and audit defaults, both about keeping a caller from choosing how large something is: the two bounds below cap caller-supplied fields before they are stored, and record only what fits rather than what was sent.
- A pending authorization request stores the client's fields bounded — redirect URI 2 KiB, `state` 512 bytes, `code_challenge` exactly 43, scope one entry — and a request refused for an over-long `state` does not echo it back, because RFC 6749 asks for the state in the error redirect and echoing a megabyte would only move it into a `Location` header. A client that packs a JWT into a state larger than 512 bytes is refused. Details: `.agents/docs/mcp-server.md`.
- A tool call's arguments are bounded at 64 KiB in the ledger before they are rendered, on top of the 8 KiB per string and 256 KiB per payload bounds; past that the row records that arguments came, not what they were, because the endpoint accepts a larger body and a call refused by the budget carries its arguments too. Details: `.agents/docs/mcp-server.md`.
- **The plain-HTTP anonymous routes are rate-limited by the resolved client address, in a bounded store.** OpenLineage ingestion and each OAuth route carry their own limiter, keyed by the client address resolved through `--trusted-proxies`; that list must name proxies rather than client ranges, because an entry covering the client itself makes the chain fall back to the caller-written segment. The store caps the identifiers it tracks, sweeps idle buckets and drops an arbitrary one at capacity, and each route writes a ledger row per request, so its row rate is bounded by the same bucket. A deployment-wide bucket shared by every identifier was tried and removed: a caller rotating identifiers exhausted it and every other producer got `429`, converting an unbounded rate into a way to deny everyone else. The limiters are process-local. Details: `.agents/docs/rate-limiting.md`.
- **An MCP token can be revoked, and every anonymous OAuth route is rate-limited.** `Logout` accepts a token this server signed without requiring a particular audience, so an MCP token has a self-service remedy beyond expiry. Registration, the token exchange, `/oauth/authorize` and `/oauth/authorize/complete` each carry their own per-address ceiling rather than one shared ceiling — merging them would tighten the anonymous OAuth surface four-fold and would turn the integration suite red, so they stay separate. A `404` from a switched-off surface is deliberately not written to the ledger. Details: `.agents/docs/rate-limiting.md`, `.agents/docs/mcp-server.md`.
- **Editing a data source's connection parameters is an administrator action, not an authorization boundary.** `extra_connection_parameters` reaches the driver's own connection syntax unchanged, and the existing blacklist checks parameter names only, so a value can still introduce another parameter; it is a guard rail for an honest configuration, not a boundary. Whoever can write the field already holds the instance write permission and could set `host` or `password` on the same resource, so a whitelist would constrain a decision that caller is trusted to make. Details: `.agents/docs/security-open-items.md`.
