# Security and deployment posture

These are deliberate, accepted decisions — not open bugs. Each is a knowingly chosen trade-off for a self-hosted, single-database deployment, so correcting one needs a subsystem-level decision.

Each item's maintenance reference holds the detail; this page states the decision and its cost.

## Authorization and accounts

- **Authorization is workspace-scoped (single tenant).** Every authenticated `workspaceMember` can read all instances, databases, metadata, lineage, OpenLineage data and the user directory; writes need `workspaceAdmin` or an explicit `permission` annotation. Per-resource IAM would be a subsystem-level change, so the read baseline stays. See `.agents/docs/iam-and-permissions.md`.
- **Signup is open until an operator closes it, and the first account becomes the workspace administrator.** The first active `END_USER` becomes `workspaceAdmin`; signup works until `DisallowSignup` is set, so anyone reaching the port can register and read everything. Closing it is the operator's decision. See `.agents/docs/iam-and-permissions.md`.
- **`allUsers` is server-managed and carries the member baseline only.** It matches every authenticated principal, so it may be bound only to `roles/workspaceMember`, and a replace that drops that binding is refused; the "at least one administrator" guard keeps it manageable. See `.agents/docs/iam-and-permissions.md`.
- **An account is identified by its user ID; email is administrative, and SSO binds to the provider's subject.** An IdP login resolves the stored `(provider, subject)` binding, never the email claim, so an existing account is not adopted by an email match. A workspace can opt out **for named identity providers** with `sso_email_identity_idps` (empty by default): through such a provider the login is identified by email, and an existing account with that address is taken over, its password replaced and earlier sessions invalidated. Listing a provider asserts it verifies addresses for one person, because an address claim anyone can set names an account anyone can sign in as. See `.agents/docs/sso.md`.
- **An identity provider's client secret is encrypted, and its row is the trust anchor.** `IdentityProviderService` is the only write path and no read returns the secret; an undecryptable row is never read as plaintext — login and `Get` refuse it, and the anonymous provider list skips it so one bad row cannot remove every sign-in button. An account binds to `(provider id, subject)`, and deleting a provider leaves its bindings, so re-creating the id revives those accounts. See `.agents/docs/sso.md`.
- **SSH bastion host keys are verified per data source, not against a server-side file.** Each data source carries its trusted host key in `ssh_host_key`, and a connection is refused when the list is empty or the key is missing, because the tunnel carries credentials. Whoever may set `ssh_host` also chooses the key it must present, so no operator logs in to the server.

## Credentials and sessions

- **Stored credentials are encrypted, and whether database read access is enough to recover them is the deployment's choice.** Credentials and LLM API keys are encrypted under a database-held data key, which `METAXISDATA_ENCRYPTION_KEY` can wrap with a key kept outside. Leaving the wrapper unset is the trade-off — database read access recovers every credential. Losing or hand-editing the key makes credentials unreadable and the server refuses to start. Rows from the retired scheme read back **empty**, never migrated. Audit redaction misses `ssl_ca`; database write access is outside this item. See `.agents/docs/credential-encryption.md`, `.agents/docs/sso.md`, `.agents/docs/security-open-items.md`.
- **The CLI stores its session in clear text.** `mxd` saves the device-login access token and rotating refresh token to `~/.config/metaxisdata/config.json` or `$METAXISDATA_CONFIG` (mode 0600); neither is printed. The access token lives seven days, and the session is a **connected app**: only the refresh digest is stored, rotation is single-use, and the 30-day lifetime slides. Revoking it in **Connected apps** cuts the access token within 30 seconds and ends the refresh chain; `mxd auth logout` ends **this machine's** connection only; a keychain dependency was judged not worth it. See `.agents/docs/cli-mxd.md`, `.agents/docs/refresh-tokens.md`.
- **A web session has its own rotating refresh token, in the database.** A `web` login sets a seven-day access cookie and a refresh token with a 30-day absolute lifetime; rotation is single-use and inherits the original deadline, so a session cannot be extended indefinitely, and `Logout` deletes the row. Only the digest is stored. See `.agents/docs/refresh-tokens.md`.
- **A revoked access token stays revoked, in the database.** `Logout` records the token's `jti` in `revoked_token` with the token's own expiry, so every entry point refuses it and a restart does not revive it. A replica caches the decision for at most 30 seconds, so cross-replica behavior depends on one replica or sticky routing. Logout also ends what could replace the token: it deletes the web refresh row, and for an MCP token revokes every connected app that client holds, keeping the rows so the page shows what ended. See `.agents/docs/refresh-tokens.md`.
- **`mxd` talks to one server, and the token only goes there.** The HTTP client refuses any redirect off the address `--server` names and sends the `Authorization` header only there. Following the redirect anonymously would be worse: a redirect off the one server is a misconfiguration or an attack. See `.agents/docs/cli-mxd.md`.
- **Analysis scopes live only in the process environment.** `mxd` reads `METAXISDATA_SCOPES` per invocation and never writes it anywhere; several agents share a machine for different projects, so a remembered set would be overwritten by whichever ran last. Which scopes a project uses stays the user's decision. See `.agents/docs/cli-mxd.md`.

## The single-process assumption

Several features keep state in the process, so a deployment runs one server replica. There is no leader election or advisory lock; sticky routing, or the cost, is the operator's call.

- **Background runners keep their state in the process.** Sync queues, retry backoffs, per-database and per-instance gates, `SyncOperation` records, analysis queues and refresh clocks live in memory. A second replica would duplicate every sync and analysis, split sync-result messages, and race derived rows. A restart loses queued work but converges: the instance scan re-enqueues databases and the hourly scan re-queues stale objects. See `.agents/docs/runner.md`.
- **Device login state is process-local.** Create, approve and exchange must reach the same replica. Approval reuses the approver's web session and skips the password policy, which would otherwise lock SSO-only users out of the CLI. See `.agents/docs/cli-mxd.md`.
- **SSO login state is process-local.** `CreateSSOState` mints a single-use nonce in a bounded in-memory LRU that the login consumes, so starting and finishing a sign-in must reach the same replica or the callback is refused. The nonce is the anti-CSRF check, not the browser-side `state` alone; a database-backed nonce would remove the single-replica requirement. See `.agents/docs/sso.md`.
- **The untimed user cache is process-local too.** A field written on one replica (the UI language) can be answered from the previous value on another until the entry evicts or the user is written.

## Audit ledger and request budgets

- **`audit_log` and `meta_registry_resource_history` are kept forever.** Maintenance prunes caches, logs, runs, expired tokens and grant rows, but never the ledger or metadata history. What matters is **rows per call, not calls**: limits bound call frequency, while one call can write many rows into a table they never look at — a schema sync writes one row per changed object, and `BatchSyncInstances` takes up to 1000 instances. Retention is paired with a write bound; the read baseline is not audited, so it writes no row. See `.agents/docs/rate-limiting.md`.
- **Choosing a UI language writes a `User` row, and therefore a permanent audit row.** The SPA stores the chosen tag in `User.language` because the Explain SQL answer follows the user's language; updating your own user needs no permission, but `UpdateUser` is audited, so a switch leaves a ledger row with the request and response. The SPA writes only when the value differs, so a switch costs one row.
- **The anonymous credential endpoints are budgeted per source and globally.** Each carries a fixed-window budget keyed by the resolved client address with a deployment-wide backstop; `Refresh` shares Login's budget and `Logout` has its own. A refused request is answered before the audit interceptor, so it leaves no row. The shared global counter is the loose-address trade-off: one exhausted ceiling blocks everyone for the window. See `.agents/docs/rate-limiting.md`.
- **A signed-in caller's ledger writes are budgeted per principal, and the refusal is the backpressure.** Every authenticated method that writes a permanent `audit_log` row — plus `ExplainSQL` and `FetchLLMModels` — has a fixed-window budget keyed by `(principal, method)` and one deployment-wide counter (3000/min and 30000/min). It runs before the audit interceptor, so a refused request leaves no row: the ledger records every action, and a looping caller is told to slow down. The counters are process-local and deliberately loose. Three costs are accepted:
  - **The counter is spent before the permission check.** The budget interceptor precedes the ACL interceptor, so a call the caller is not allowed to make still counts — and still leaves a row, since the audit interceptor also runs first.
  - **The deployment-wide counter is shared, so one account can spend it for everyone.** An account with no permissions can exhaust the 30000/min ceiling in about half a minute, after which every other principal is refused `resource_exhausted` until the window rolls. That availability cost buys the bound on total ledger growth.
  - **`ListAuditLogs` is exempt, and that exemption is unbounded.** It is the one audited method that only reads, so the "ledger write" rule does not cover it — but a refused read still writes a row, after the audit interceptor and before the ACL denial. Any signed-in account can grow the permanent ledger without limit; bounding it means treating a read that writes as a ledger write.
- **A limiter's table is only pruned at its ceiling.** Elapsed keys are dropped only when the map is full, so a long-running process accumulates every key it has seen, and a full walk of the map under the limiter's mutex happens on each request past the ceiling. Keys are server-chosen, so this is a tail-latency boundary, not a denial of service. See `.agents/docs/rate-limiting.md`.
- **The plain-HTTP anonymous routes are rate-limited by the resolved client address, in a bounded store.** OpenLineage ingestion and each OAuth route carry their own limiter keyed by that address through `--trusted-proxies`, which must name proxies rather than client ranges: an entry covering the client makes the chain use the caller-written segment. Each route writes a ledger row per request, so its row rate is bounded by the same bucket. A deployment-wide bucket was tried and removed: a caller rotating identifiers exhausted it and everyone else got `429`, turning an unbounded rate into a way to deny everyone. The limiters are process-local. See `.agents/docs/rate-limiting.md`.
- **Bulk data-quality exports and the target report are audited reads.** The three streamed CSV exports and the report deviate from the read baseline: a bulk egress is recorded once per call (who, which filters, how many rows), because the audit trail must name who pulled 100,000 rows. The report body must not enter the permanent ledger: its field is redacted by name, so the row drops the document. Because the rows are permanent and the reads heavy, they are budgeted like writes, capped at 100,000 rows per export, and a process streams four at once (`ResourceExhausted`, never queueing); the report warns that forwarding the file forwards those rows, being the one export with sample values — the CSVs never include them. See `.agents/docs/data-quality.md`.
- **Application SQL reporting has no request budget, and what it stores is bounded by the application instead.** `POST /api/v1/applicationSql/report` is the only machine-ingest route with neither a rate limit nor a limiter store: it adds a row per *distinct statement*, and statements come from source code rather than request volume, so a budget would bound the wrong quantity. The bound is a trust boundary: a key is issued by hand to the operator's own application, and an unparseable statement is refused rather than stored. A key that invents distinct *valid* statements can still grow the table one row per statement. Costs: a compromised or looping key can spend the CPU on parsing, because the route sits outside the Connect interceptor chain and has no budget; and per-request audit rows are not written — the key carries counters, because the ledger is kept forever and machine traffic grows it with request volume. See `.agents/docs/application-sql-ingestion.md`.
- **A notification stream is authenticated once, and ends itself.** `SubscribeNotifications` is authenticated like the rest of its service and deliberately not audited; authentication happens at the handshake and is not re-checked, so the server ends every stream after 30 minutes and the reconnect re-authenticates, which lets a logout or revocation take effect inside that window. The fan-out is process-local, so a multi-replica client must reconnect to see a message written elsewhere. See `.agents/docs/notifications.md`.

## MCP, OAuth and the agent surface

- **The MCP surface is off by default and needs `external_url`.** `mcp_enabled` gates the endpoint and every `/oauth/*` route, all of which answer 404; enabling it requires `external_url`, because the issuer and resource identifier are derived from it and never from the request's `Host`. See `.agents/docs/mcp-server.md`.
- **MCP tokens are bound to the MCP resource, and to nothing else.** The token carries the canonical `<external_url>/mcp` as its `aud`, so a web or CLI token is refused at `/mcp` and an MCP token is refused on ConnectRPC. Changing `external_url` therefore invalidates every outstanding MCP token and stored grant; Connected apps shows those connections as `REAUTH_REQUIRED` rather than silently revoking them. See `.agents/docs/mcp-server.md`.
- **The MCP authorization server is self-contained, and issues rotating refresh tokens.** Registration is open (RFC 7591, public clients only) with PKCE S256, but a token needs a signed-in user's approval on `/oauth/consent`; the access token lives seven days, and the opaque rotating refresh token is stored only as a digest and consumed single-use in place. Revoking a connection (from Connected apps, or by `Logout`) refuses its access tokens within 30 seconds (immediately locally) and makes its refresh token mint nothing; a revoked row is never cleared, so authorizing again creates a new connection. Pending requests and codes are process-local, so approval and completion must reach the same replica; refresh may reach any. See `.agents/docs/mcp-server.md`, `.agents/docs/refresh-tokens.md`.
- **An MCP token can be revoked, and every anonymous OAuth route is rate-limited.** `Logout` accepts a token this server signed without requiring an audience, so an MCP token has a self-service remedy. The connection can also be revoked directly from the management page by its owner or an administrator. Each anonymous OAuth route carries its own per-address ceiling rather than one shared ceiling — merging them would tighten the surface four-fold and turn the integration suite red. A `404` from a switched-off surface is not written to the ledger. See `.agents/docs/rate-limiting.md`, `.agents/docs/mcp-server.md`.
- **The MCP endpoint is stateless, cross-origin protected, budgeted and time-bounded.** It keeps no session, so every request is authenticated; it relies on the standard library's cross-origin protection because the SDK applies none. A principal gets a per-minute call budget and a request may take at most 60 seconds, because that budget cannot see an invalid token, every request is also counted against the resolved address before the bearer check. The counters are process-local. See `.agents/docs/mcp-server.md`.
- **MCP audits every tool call; the built-in agent audits only its writes and proposals.** The MCP endpoint is a remote entry point a model drives, so every call — reads and refusals included — writes one ledger row. The built-in agent runs in-process and already records every message, tool call and result in its transcript; auditing its reads again would grow the ledger with daily polling, so only `SideEffect != None` tools write a row. See `.agents/docs/agent-platform.md`, `.agents/docs/data-quality.md`.
- **Every MCP tool call is audited, reads included, and its arguments are bounded.** The ConnectRPC read baseline is not audited; the MCP surface deliberately is, because a model drives it, and a refused call leaves a row too. Those rows are permanent, so arguments are redacted and bounded at 64 KiB before rendering; past that the row records that arguments came, not what they were. See `.agents/docs/mcp-server.md`.
- **A pending authorization request stores the client's fields bounded.** Redirect URI 2 KiB, `state` 512 bytes, `code_challenge` exactly 43, scope one entry; a caller must not choose how large what the server stores is. An over-long `state` is refused without echo, because RFC 6749 would put it in the error redirect and a megabyte would only move into a `Location` header. See `.agents/docs/mcp-server.md`.
- **A quality agent's front office and work sessions are owner/admin reads.** The conversation RPC is readable by the owner and administrators, while sending is owner-only (ownerless falls back to administrators). The per-target work-session list, detail and transcript are product reads too: the agent's owner and administrators may read them, and an unauthorized caller gets `NotFound` rather than learning that a session exists. These reads follow the un-audited read baseline; resuming a stuck session is the only administrator action and it is audited. The transcript shows tool arguments and results and model reasoning when the provider returns it; tool results carry identifiers, counts and memory statements, never sample rows. Transcripts and compaction checkpoints are kept indefinitely. See `.agents/docs/data-quality.md`.

## Destructive and derived data

- **Destructive schema sync is log-only.** When a snapshot no longer contains an object the runner deletes it and records the GUIDs; there is deliberately no shrink threshold or confirmation flag, and a privilege change can empty a MySQL `information_schema` snapshot, so the deletion log is the only trace. A database row's `deleted` flag is **single-directional**: hiding follows any observation that the target no longer has the database, while only instance enumeration revives it. See `.agents/docs/schemasync.md`.
- **Failure samples are raw row data, stored by default.** With `store_failure_samples` on (the default), a completed execution keeps up to `failure_sample_limit` (20, maximum 100) failed rows — for a column check, the checked column plus recorded primary-key columns — each value truncated to 256 bytes. Turning it off records counts only. The values never leave the deployment unless an operator enables `send_sample_values_to_llm`, which is off by default and gates raw profile values into the agent's context. See `.agents/docs/data-quality.md`.
- **OpenLineage ingestion bounds one event, and the pages read stored columns rather than payloads.** One event is capped at 1 MiB inside an 8 MiB request body, and an oversized event is refused with `413` rather than stored and failing its insert forever. The run, task, dataset and filter pages read extracted columns and aggregate rows, not a page's worth of `raw_payload`, and the ledger's write rate is bounded by the interceptor budget. See `.agents/docs/openlineage-lineage.md`, `.agents/docs/rate-limiting.md`.
- **A link the server derives from caller-supplied data is a web address or nothing — but it may still be any web address.** The Airflow `log_url` facet is bound to an `href`, so only an absolute `http`/`https` URL with a host survives; that removes script execution, not link injection, since a valid `http(s)` URL to a phishing page still reaches the button, so the remaining bound is trust in whoever holds an ingestion key. The SPA re-checks the same whitelist.
- **Editing a data source's connection parameters is an administrator action, not an authorization boundary.** `extra_connection_parameters` reaches the driver's connection syntax unchanged, and the blacklist checks parameter names only, so a value can still introduce another parameter; it is a guard rail for an honest configuration, not a boundary. Whoever can write the field already holds instance write permission and could set `host` or `password` on the same resource, so a whitelist would constrain a decision that caller is trusted to make. See `.agents/docs/security-open-items.md`.

## Outbound notifications

- **Outbound channels are administrator-chosen destinations, and their endpoint URL is a credential.** A channel is set by an administrator, so the destination is trusted like a database connection: the deployment will POST to any `http`/`https` address an administrator enters, even inside its network. That SSRF surface is accepted rather than allowlisted, because the same administrator can point a data source anywhere. The endpoint URL and signing secret are ciphertext in `notification_channel.secret`, never returned by a read. The SMTP password is encrypted and write-only too; an email channel resolves recipients at send time, so the payload holds audience user ids, not addresses, and the generic webhook body carries no row data. The weekly quality digest has no audience and no inbox copy: only channels naming it explicitly opt in (an empty list does not), routing rules never select it, and address-less email channels are skipped. Delivery is asynchronous: a failed attempt is retried with backoff and becomes dead after six attempts, so a broken destination cannot fail the producer. Redirects are not followed for any HTTP kind — a redirect would move a signed body to a host the administrator never named. See `.agents/docs/notifications.md`.

## Transport and transport-adjacent defaults

- **gRPC reflection is anonymous.** The registered service and message definitions are public, so the port must not be exposed to untrusted networks.
- **Reverse-proxy contract.** Cookie-based writes trust `Origin`/`Sec-Fetch-Site`, and audit records believe `X-Forwarded-For` only from peers listed in `--trusted-proxies`; without the proxy listed, CSRF requests can look same-origin and audit IPs collapse to the proxy. The chain is read from the right and stops at the first hop not listed as a proxy, so the caller-chosen leftmost entry is never used. See `.agents/docs/rate-limiting.md`.
- **The REST gateway's own hop never decides the client address.** `/v1/*` is answered by grpc-gateway dialing the server's own port, so the Connect handler's peer is loopback; the gateway stamps the outer peer with a process-local HMAC proof the audit layer trusts only when it verifies. Loopback need not be listed in `--trusted-proxies` for the gateway's sake, though a same-host proxy in front of `/v1/*` is listed for its own hop. See `.agents/docs/rate-limiting.md`.
- **Every response carries a fixed document policy, and the SPA cannot be framed.** Every response gets the same CSP with `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`, so `/device` and the OAuth consent page cannot be embedded and approved for a victim. No `Strict-Transport-Security` is sent, because it needs a trustworthy https signal the middleware cannot obtain, and the Vite dev server sends none of them, so a development page is outside the policy.
- **Prometheus metrics are pull-only, off by default, and served without authentication on their own port.** Setting `--metrics-addr` (`METAXISDATA_METRICS_ADDR`) starts a dedicated listener serving `/metrics` from a private registry; the API port never serves it, and `--debug` does not enable it. Instruments carry bounded operational counts and never instance, database, table, GUID, SQL or user data as a label. Being anonymous, it belongs on a trusted interface or inside the network boundary. See `.agents/docs/metrics.md`.
- **Every ConnectRPC unary call has a server-side deadline, and the streaming ones do not.** A unary handler is cancelled after 60 seconds and answers `DeadlineExceeded` with a fixed message; the methods whose work legitimately runs longer (a column profile's queries, a schema sync) get twenty minutes. The bound is cooperative — store queries and LLM HTTP calls honour their context, but a handler that ignores it is not preempted. Streaming endpoints are exempt by construction, and `/mcp` has its own, harder 60-second wall.
