## Verdict

**approve with fixes** — **0 blockers, 2 majors, 11 minors, 8 nits.**

The design is coherent: quiet hours hold (never drop) without spending the retry budget, channel-level bypass, an additive routing model with an explicit `routed_only` opt-in, and a read-only, pure-function schedule evaluator that is easy to test. The two majors are both in the quiet-hours deferral contract rather than the routing model: (1) a DST spring-forward day can turn a canonical nightly window into a **24-hour hold** (verified with the shipped function), and (2) a deferred delivery is rescheduled to an absolute instant that nothing can shorten, so a schedule change or disabling quiet hours does **not** release held deliveries — contradicting the public API comment — and a typo'd far-future maintenance window silences outbound alerting indefinitely. Routing has no correctness blocker; its issues are silent-config-failure traps (owner/group not validated, dangling channel blocking updates) and an untested fail-open path.

## Majors

### M1 — A DST spring-forward day can turn a nightly quiet window into a 24-hour hold

**Where**: `backend/component/notification/outbound/schedule.go:119-146` (`quietWindowEnd`; the cross-midnight branch at `:141-142`).

**Failure scenario**: on the spring-forward date, a window whose `start`/`end` both fall in the DST gap normalises to the *same* instant via `time.Date`; the code reads "end not after start" as "crosses midnight" and adds a day, producing a 24-hour window. Verified by calling the shipped `QuietUntil` with `Europe/Paris`, window **Sunday 02:00–03:00**, on 2025-03-30:

```
Sun 2025-03-30 02:00 CEST -> quiet=true until=2025-03-31 03:00 CEST (24h0m0s)
Sun 2025-03-30 12:00 CEST -> quiet=true until=2025-03-31 03:00 CEST (15h0m0s)
```

Every non-bypass outbound delivery on that Sunday (and Monday 00:00–03:00) is held up to a day; bypass channels are unaffected. The same collapse occurs for `America/New_York` on 2025-03-09 with the canonical `01:00–02:00` / `01:30–02:30` nightly windows and for `Australia/Sydney` on 2025-10-05 with `02:00–03:00` — i.e. the most common quiet-window shapes, once a year, silently. There is no DST test in `schedule_test.go`, and the docs do not mention DST.

**Fix**: distinguish "crosses midnight by intent" (`parsedEnd < parsedStart`) from "DST normalisation collapsed the bounds" (`parsedEnd != parsedStart` but `windowEnd.Equal(windowStart)`). For the latter, resolve the end from the intended wall duration instead of adding a day — e.g. `windowEnd = windowStart.Add(time.Duration(((endMin-startMin+1440)%1440)) * time.Minute)` — or cap the computed window at 23 h and fail open (treat it as malformed) so a bad schedule can never hold alerting for a day. Add cases to `schedule_test.go`: `Europe/Paris` 2025-03-30 `02:00–03:00`, `America/New_York` 2025-03-09 `01:00–02:00`, and the fall-back dates (2025-10-26 / 2025-11-02) to pin the expected duration.

### M2 — Held deliveries cannot be released early, and the API comment promises they can

**Where**: `backend/runner/notificationdispatcher/notificationdispatcher.go:150-206` (defer) + `backend/store/notification_delivery.go:206-233` (`DeferNotificationDelivery`), against `proto/v1/v1/setting_service.proto:95-99` ("Disabling it clears the schedule and **releases every held delivery on the next dispatcher tick**") and `backend/api/v1/setting_service.go:667-700` (`UpdateQuietHoursSetting`).

**Failure scenario**: a notification that falls inside a window is written as `PENDING` with `next_attempt_at = <window end>` (`dispatcher.go:163`, `:192-193`) — an absolute instant, and the row carries **no marker distinguishing a quiet-hours deferral from a normal retry backoff**. Consequently:
- an administrator who disables quiet hours (or shortens the window) mid-window to release an incident alert sees **nothing released**: the row stays `PENDING`, is not due, and is not claimed until the *original* window end (could be 8+ hours). `UpdateQuietHoursSetting` only writes the setting; nothing resets deferred rows. The proto comment above is therefore false, and it is also wrong about "clears the schedule" — disabling just stores `enabled=false` with the schedule kept.
- a maintenance-window typo (e.g. end year 2035 — a `datetime-local` value, validation only checks `start < end`, and there is no duration cap) silences **all** non-bypass outbound alerting indefinitely. The rows are `PENDING` forever (the maintenance prune only removes `SENT`/`DEAD`), and fixing the schedule later still does not recompute their `next_attempt_at`. An admin can only notice via the Deliveries card showing `pending` with a far-future next attempt.

**Fix**: keep deferrals identifiable and releasable — add a marker in migration `0034` (e.g. `deferred BOOLEAN NOT NULL DEFAULT FALSE` or a `defer_reason`/`hold_until` column), set it in `DeferNotificationDelivery`, and on a successful quiet-hours update run `UPDATE notification_delivery SET next_attempt_at = NOW(), deferred = FALSE WHERE state = PENDING AND deferred`; a dispatcher tick that sees `quiet == false` can also flush marked rows. Also cap a maintenance window's duration in `ValidateQuietHoursSetting` (e.g. ≤ 30 days) and in the UI. If a marker is out of scope for this PR, at minimum correct the proto comment and document the limitation — but the starvation path should not ship undocumented.

## Verified as correct (no need to re-check)

**Schedule correctness (scrutiny 1)**
- Windows are evaluated in the configured IANA zone (`time.LoadLocation`, `now.In(location)`), and a bad zone/unreadable clock fails open per window — tests pin `nil`/disabled/bad-zone/bad-clock.
- Boundaries are start-inclusive, end-exclusive for recurring windows (`!Before(start) && Before(end)`) and `[start, end)` for maintenance windows; both are tested (`TestQuietUntilRecurringWindow`, `TestQuietUntilMaintenanceWindow`).
- Cross-midnight windows: an end at or before the start adds a calendar day with `AddDate` (which keeps wall-clock time across DST rather than adding 24 h); both late-night and early-next-day coverage are tested.
- Multiple active windows resolve to the **latest** end (`end.After(until)`), which is the correct "still quiet" answer; maintenance and recurring windows are combined the same way.
- Past/inert maintenance windows are skipped; a window ending exactly now is handled by the dispatcher guard (`!until.After(now)` → attempt normally).
- Validation: enabled requires an IANA timezone and at least one window; ≥1 day per window, valid ISO weekdays, `HH:MM` range checks, `start != end`, caps of 20 recurring + 20 maintenance, maintenance requires both timestamps and `start < end`; a disabled schedule is accepted as-is. The API additionally rejects protobuf timestamps that are not valid instants (`CheckValid`) and de-duplicates days, owners, groups, channels and event types.
- The UI converts maintenance instants to/from `datetime-local` in browser-local time and round-trips the instant exactly (test asserts the saved `seconds` for a UTC instant); the curated timezone list always includes the browser zone and any stored zone, so a stored non-listed IANA zone is never lost.

**Deferral semantics (scrutiny 2)**
- A quiet-hours delivery is deferred **before** any adapter call (the tests assert zero endpoint hits), stays `PENDING`, `next_attempt_at` is the window end, and the claim's `attempts + 1` is given back with `GREATEST(attempts - 1, 0)` — the retry budget and the DEAD threshold are untouched; the SQL shape is pinned by a store test.
- `bypass_quiet_hours` channels in the same batch are attempted normally (tested); a delivery whose channel is missing falls through to the normal attempt path (and is dead-lettered as before, not deferred).
- Quiet-hours evaluation happens once per batch, after claims; a read failure logs and fails open; a window end already past also attempts normally. The metric outcome `deferred` is added and documented in `.agents/docs/metrics.md`.
- Manual retry still resets `attempts = 0`; a retried delivery that lands in a quiet window is deferred without consuming that retry. `DeferNotificationDelivery` is idempotent for one dispatcher because the deferred row is not due again until the window end.

**Routing (scrutiny 3)**
- Model is additive and correctly gated: every channel still passes its own `enabled` + `event_types` + `min_severity` filter; a `routed_only` channel is skipped unless a matching rule selected it; ordinary channels are unaffected by rules (tested both ways); a disabled rule selects nothing (tested).
- Audience source is the event-level audience written by `Send` (the recipient) and `SendToWorkspaceAdmins` (all admins), which is the right "who does this concern" definition for owner/team routing; owner filters compare numeric user ids, group filters expand IAM groups' members (`users/{id}` via `common.GetUserID`, matching the group-service storage convention) and compare against the same ids; group emails are lowercased on write and on match; owners are normalised to `users/{id}`; channels are normalised from resource names to ids and de-duplicated; empty match fields are wildcards and a fully empty match matches every event (documented in proto + proto store + operator docs).
- A route-selected but deleted channel is skipped at enqueue, the rule's other channels still deliver (proto contract), and unknown channel ids are rejected at create (`InvalidArgument`); a route's own type/severity filter is applied before channel selection (tested).
- Enqueue routing is best effort: a route read error logs and only affects `routed_only` channels (documented in the failure table); routing is computed once per event (not once per recipient row), so a multi-admin event fans out identically for all channels.
- `notification_route` storage: unique `resource_id`, JSONB payload of the documented `proto/store NotificationRoute`, resource ids generated with the valid-alphabet `RandomResourceID` (the PR-2 round-trip guard applies), and `GetNotificationRouteID` validates the name shape. ## Suggested fix order

1. **M1** — DST collapse fix + DST tests in `schedule_test.go`; the fix is contained to `quietWindowEnd` and prevents a once-a-year 24 h alert blackout.
2. **M2** — decide the release story: add the deferral marker (migration + store + quiet-hours update release) and the maintenance-window duration cap, or, as a minimum for this PR, correct the proto comment and document that a schedule change does not release held deliveries. The starvation path should not ship silent either way.
3. **Minors 1–3** — routing config traps and the missing fail-open tests (dangling channel on update, owner/group existence validation, route/group/quiet read-failure tests) — small, high-value for an alerting feature.
4. **Minors 4–11** and the nits; the checkbox coverage gap (minor 8) is the only frontend item that could hide a regression.
