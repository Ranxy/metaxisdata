## What it is

Two independent single-use rotating flows: the MCP OAuth 2.1 server at `/oauth/*` and the SPA web session. Both store only the SHA-256 hex digest of an opaque token; both are single-use, so two concurrent refreshes race and exactly one wins, and a replay is `invalid_grant` (MCP) or `Unauthenticated` (web). The MCP rotation is an in-place `UPDATE … RETURNING id`; the web session consumes with `DELETE … RETURNING` and inserts a replacement. The MCP row is also the durable record of one **connected app** (one user × one client authorization), which is why its id must survive rotation. Refresh tokens live 30 days (`DefaultRefreshTokenDuration`), while access tokens live one hour: an MCP access token and a web session access token each get `MCPAccessTokenDuration` / `DefaultAccessTokenDuration` from `backend/api/auth/auth.go`. The CLI's device-login token predates both flows and keeps its seven-day lifetime. The schema is additive; no legacy-token fallback exists.

## Decisions

- **A refresh token is a digest, never a secret at rest** — a database read hands out no usable credential, and a 256-bit random string needs no slow KDF, so a lookup stays one indexed read.
- **Web sessions are keyed by `user_id`** — an account is its principal id; the administrative, mutable email address would let a change orphan or adopt a session.
- **Every refresh re-validates the principal from persisted state** — a deactivated account, and a grant issued before the last password change, are refused, exactly as `TokenAuthenticator.Resolve` refuses an access token. The rotated row therefore carries the original issue time forward, so the rule survives rotation.
- **Web rotation keeps an absolute session lifetime; the MCP grant slides** — the web token inherits the original issue time and deadline, so refreshing cannot extend a session indefinitely; an MCP client in use has no natural point to re-authorize, so its grant's expiry moves on activity.
- **The MCP grant row is the connected app, so rotation updates it in place** — the row id is what the management API addresses and what the access token's `gid` claim carries; a delete-and-insert would change it on every refresh and let a revocation land on a row that no longer exists. Rotation and revocation therefore serialize on one row, and a revoked row is terminal: no path clears `revoked_at`, and authorizing again creates a new row with a new id.
- **Revocation covers what could replace the credential** — `Logout` deletes the web row its cookie names, and for an MCP token (whose `cid` claim names its registration) it **revokes** every grant that client holds for that user, so revoking one token ends the connection rather than leaving it one refresh from a new pair. A client can do the same for its own connection with RFC 7009 `POST /oauth/revoke`, presenting either credential: both address the same grant row, so an access token revokes the refresh token beside it and vice versa, and the endpoint answers every unknown, expired or forged token with the same empty `200`. The rows are kept (revoked, not deleted) so the connected-app page can show what ended; maintenance reclaims them after the retention window.
- **Already-issued MCP access tokens carry the grant id** — `TokenAuthenticator.Resolve` checks that the connection is still live behind a 30-second `GrantRevocationCache`, so a revocation stops outstanding tokens too (immediately on the replica that performed it, within 30 seconds elsewhere). A token minted before the claim existed is refused at `/mcp`; its client recovers with one refresh, because the refresh row survives the upgrade.
- **The MCP grant set is validated but not persisted** — one client shape (public, authorization code + PKCE), so `grant_types` is only checked against the supported set at registration (`backend/api/oauth/register.go:176`) and advertised back in the metadata (`backend/api/oauth/metadata.go:152`).

## Invariants

1. **MCP refresh checks before it rotates, then re-checks the live principal** (`backend/api/oauth/token.go:158`–`:241`): client binding, row presence, expiry, `revoked_at`, `resource` equals the current endpoint, and a requested scope identical to the consented one all run first, so a client-correctable refusal does not burn the credential; only then does the atomic in-place rotation decide the winner (`RotateOAuthGrant`, `backend/store/oauth_grant.go:195`). A principal that no longer exists, is deactivated, or has a password change newer than the grant ends the grant: the row is explicitly revoked (`revokeFailedGrant`) because the rotation no longer deletes it.
2. **Web refresh consumes first, then re-reads the principal** (`backend/api/v1/auth_service_refresh.go:63`), refuses deactivation and a pre-password-change session, and re-stamps the rotated token with the original `IssuedAt` **and** `ExpiresAt`; the MCP rotation also keeps `created_at` while re-stamping its expiry from now, which is what lets the password-change cutoff still order it.
3. **Refusal codes are part of the contract:** replay/unknown/other-client/expired/revoked → `invalid_grant`; a differing requested scope → `invalid_scope`; an expired grant is refused and its row is **kept** (maintenance reclaims it, and the page shows `EXPIRED`); web refusals are `Unauthenticated`.
4. **The access-token check is the grant's liveness, not the refresh credential's.** MCP access tokens carry `gid`; `TokenAuthenticator.Resolve` looks up `(id, user_id, client_id)` with `revoked_at IS NULL AND expires_at > NOW()` (`IsOAuthGrantLive`, `backend/store/oauth_grant.go:248`) behind a **separate** 30-second `state.GrantRevocationCache`. A missing row is not live (the refresh credential outlives the access token, so a pruned row cannot hide a token that should work); a read failure fails closed. `/mcp` refuses a token without `gid` (`backend/mcp/auth.go:60`).
5. **`Logout` revokes, it does not delete.** An MCP token's `Logout` conditionally updates every grant of `(user, client)` and marks each id in the process-local cache (`backend/api/v1/auth_service.go:328-341`). A repeated logout is an idempotent no-op; the ledger records it.
6. **Upgrade is one-shot.** An old replica running the pre-change binary rotates with `DELETE + INSERT` and could resurrect a revoked grant or drop the new columns, so the deployment must stop old replicas before the new version serves traffic; a rollback needs a database restore. Pre-upgrade MCP access tokens are refused and recover via one refresh.
7. **RFC 7009 revocation is idempotent and non-probing.** `/oauth/revoke` resolves the credential to one grant row (access token by local verification of its `gid`, otherwise by refresh-token digest), writes `revoked_at`/`revoked_by` with the credential's user, and marks the 30-second `GrantRevocationCache` after the write. An unknown, expired, forged or already revoked token, and a `client_id` that does not match the credential's owner, are all the same empty `200` with no row write; a store failure is `500` and claims nothing.
