# Data Quality — Reference

The data quality subsystem answers one question deterministically: is this data acceptable? A rule compiles to SQL (or to an in-process check) over a table, view, external table or materialized view; each run records a six-way verdict, a bounded failure sample and, when meaningful, a comparison sample of passing rows. A per-rule issue ledger turns persistent failures into a problem, and notifications carry it to the inbox and to administrator-configured outbound channels. Three LLM analyses draft rules, explain failures and suggest semantic labels; they never participate in judgment. Column profiles, semantic labels, a review queue, coverage/score read models, streamed exports, a single-target HTML report, a weekly digest, contract/plan projections and a built-in quality-agent runtime sit on top of that core.

The unit of judgment is `QualityExecution`: one rule checked once. A `quality_run` is an internal dispatch batch that belongs to exactly one target; it is exposed read-only as `QualityRun` (`ListQualityRuns` / `GetQualityRun`), has no write path, and does not change judgment semantics. Scheduling is per target (`quality_target_schedule`); rules carry no timer. Everything is single-replica by design: inflight dedupe, admission queues, LLM counters and scheduler state live in the process.

## Entities and resource names

The store tables are `quality_*` (there is no `data_quality_*` table; that prefix names the protos, the service and the handlers). The shape:

```
meta_registry_resource (read-only source of target identity)
  └─< quality_rule ──< quality_rule_revision        immutable definition history
        ├─< quality_run ──< quality_execution       dispatch batch ──> one judgment
        │                      └─< quality_issue    ≤1 unresolved issue per rule
        ├─< quality_suggestion                      review queue (label / rule draft)
        └─< quality_contract ──< quality_contract_revision   declared plan snapshots
  column_profile / column_semantic_label            keyed by table GUID + column name
  quality_target_schedule                           per target: interval or cron + next run
  quality_rule_template / quality_code_table        workspace configuration resources
  quality_llm_cache / quality_digest_send           caches and digest period ledger

quality_agent  (one row: identity + runtime config; internal principal)
  ├─< quality_agent_database                        database scope
  ├─< quality_agent_enrollment                      per-target enrollment / triage state
  ├─< quality_agent_report / quality_agent_attention / quality_agent_adoption
  └─< quality_agent_session ──< quality_agent_message   append-only transcript
quality_memory                                      confirmed asset facts written by agents
```

| Entity | Resource name | Id source |
| --- | --- | --- |
| Rule | `workspaces/{ws}/qualityRules/{quality_rule}` | random, non-recyclable |
| Execution | `workspaces/{ws}/qualityExecutions/{quality_execution}` | **database row id** — the table has no resource id |
| Internal batch (`quality_run`) | no API resource name; `resource_id` is for diagnostics | random |
| Issue | `workspaces/{ws}/qualityIssues/{quality_issue}` | random |
| Suggestion | `workspaces/{ws}/qualitySuggestions/{quality_suggestion}` | random |
| Rule template | `workspaces/{ws}/qualityRuleTemplates/{id}` | random, non-recyclable (hard delete) |
| Code table | `workspaces/{ws}/qualityCodeTables/{id}` | random, non-recyclable (hard delete) |
| Agent | `workspaces/{ws}/qualityAgents/{quality_agent}` | random |
| Agent report / attention | `workspaces/{ws}/qualityAgentReports/{id}`, `.../qualityAgentAttentions/{id}` | random |
| Agent session | `workspaces/{ws}/qualityAgentSessions/{id}` (product work-session route, owner/admin) | random |
| Target | registry GUID + `MetaType` — a `(guid, object_type)` pair | path snapshot is display-only |

`parent` accepts `workspaces/-` for the current workspace. The workspace segment of a resource name must match the deployment's single workspace, otherwise `NotFound`. The last segment of an execution name is the `quality_execution` row id because that table has no `resource_id`; lists, issue first/last-seen references and explain all resolve the same id.

## Status model

Six execution result statuses. Their precedence is a rank for rollups, not the enum numeric order: `ERROR > FAIL > WARN > NOT_EVALUATED > SKIPPED > PASS`.

| Status | Meaning |
| --- | --- |
| `PASS` / `WARN` / `FAIL` | Judged: within thresholds / past warn but not fail / past fail |
| `ERROR` | No verdict was reached: SQL, connection, permission, timeout or compile failure — a monitoring fault, never merged with `FAIL`, never opens an issue |
| `SKIPPED` | Deliberately not run: orphaned target, archived rule, another execution of the same rule is in flight |
| `NOT_EVALUATED` | Ran but had nothing to judge: zero rows after filters, `MAX(timestamp)` is NULL, aggregate NULL, no baseline |

The execution lifecycle is `PENDING → RUNNING → COMPLETED | ABANDONED`. `outcome` (one of the six) exists only on `COMPLETED`; `ABANDONED` never produces a verdict (restart sweep, admission timeout, batch timeout, terminal-write failure) and never writes a synthetic ERROR. On startup, executions and batches still `PENDING`/`RUNNING` after 15 minutes are abandoned; scheduled checks are retried within the target cycle budget, manual ones are not. A batch also has a lifecycle and a result rollup (worst rank of its executions) for internal diagnosis only.

Issues are driven by `dataquality.PlanIssueTransition`, after the verdict is committed:

| This execution | Existing open issue | Action | Notification |
| --- | --- | --- | --- |
| `FAIL` | none | create `OPEN`, first/last seen = this execution | `ISSUE_OPENED` (unless muted or folded into a storm summary) |
| `FAIL` | yes | touch: last seen, execution, occurrence count | suppressed within the 1h dedupe window |
| `PASS` and previous execution `FAIL` | yes | `RESOLVED(AUTO_RECOVERED)` | `ISSUE_RECOVERED` (unless muted) |
| `PASS` and previous execution not `FAIL` (e.g. `ERROR → PASS`) | yes | no change | — |
| `WARN` / `NOT_EVALUATED` / `SKIPPED` and previous `FAIL` | yes | touch, no auto-recovery | — |
| `ERROR` | any | no change | `EXECUTION_FAILED` to administrators, never muted |

Issue statuses are `OPEN`, `ACKNOWLEDGED`, `RESOLVED`; a partial unique index on `(rule_id)` `WHERE status <> 3` guarantees at most one unresolved issue per rule, so concurrent runs and retries cannot open two. Rule lifecycle: `ENABLED` (created enabled, joins the target's next cycle) ↔ `PAUSED` (manual or orphaned target) → `ARCHIVED` (soft delete; history retained). Pausing the last enabled check of a target sets its next run to NULL; re-enabling reschedules from the stored cadence.

Suggestions are `PENDING` (the only reviewable state), `ACCEPTED` / `REJECTED` (human decision, terminal) and `SUPERSEDED` (the server closed it because the fact now exists — a label was written or a rule was created; no `decided_by`). There is at most one `PENDING` suggestion per identity; decided history stays as decision memory.

The quality agent has `state ∈ {DRAFT, ACTIVE, PAUSED, DISABLED}` (`DISABLED` terminal) and sessions `ENABLED | BLOCKED | ARCHIVED` (running is expressed only by `lease_until`; `BLOCKED` carries a code/reason and is recoverable by owner reply or administrator resume). Agent reports are always scheduled `DAILY`/`WEEKLY`, idempotent by `(agent_id, period_key)`; there is no on-demand report.

## Core mechanisms

### Rule definition and immutable revision

Create and update share one validation chain: `ResolveTarget` (the registry row exists, its instance is not deleted, the database is not hidden, named columns exist) → `ValidateConfig` (per-type parameters, column kind and capability, referenced parent/columns) → the registry steps of `ValidateRule` (referential parent table, cross-table reference target) → `ParseFilter` → `Compile` (SQL, placeholders, args, columns) → write the current structure fingerprint into `target_meta_hash`.

A semantic change (type, target, config, severity, dimension, ...) appends an immutable revision. The rule head row and the revision row are written in one transaction guarded by `SELECT ... FOR UPDATE`; a mismatched `ExpectedRevision` returns a conflict that surfaces as `Aborted`. Executions record the revision they actually ran, so editing a rule never changes a historical verdict. Deletion is archival; revisions, executions and issues stay.

`PreviewQualityRule` is the dry run: validate, compile, then probe the read-only source with `LIMIT 0` / `TOP 0` (10s timeout) without writing anything. Metadata rules (`schema_drift`) skip the probe. Creating a query rule against an instance without a `READ_ONLY` data source is rejected with `FailedPrecondition`; if the source is removed later, execution reports `ERROR(NO_READ_ONLY_SOURCE)`. Save itself validates and compiles only.

### Compile, dialect and judgment

There are 20 rule types: `row_count`, `row_count_change`, `null_percent`, `unique`, `unique_combination`, `accepted_values`, `range`, `regex`, `string_length`, `referential_integrity`, `cross_column`, `freshness`, `custom_sql`, `cel_expression`, `schema_drift`, `group_check`, `aggregate`, `cross_table`, `standard_code`, `segment_check`.

`ruleTypeSpecs` in `rule_type_spec.go` is the single source of truth: config arm, checked columns, identity fields and discriminators, allowed object types and engines, PERCENT support, sampling support, score mode, compile/validate/evaluate/failure-sample/aggregate-observation/label-draft behavior. Everything derives from that row; adding a rule type means a proto enum value, one table row and the per-type functions it needs, and the contract test in `rule_type_spec_test.go` fails on omissions. A compiled rule is `CompiledQuery{SQL, Args, Kind, Columns}` where `Kind` is aggregate (one row), failed rows, sample rows or metadata (no SQL).

Dialect families: MySQL family / TiDB / MariaDB / OceanBase / StarRocks / Doris (backtick quoting, `?` placeholders, `LIMIT`, `REGEXP`, `CHAR_LENGTH`), PostgreSQL (double quotes, `$n`, `~`), MSSQL (bracket quoting, `@pN`, no regex, `LEN`, `TOP 0` probe). Identifiers are always quoted and values always parameterized; placeholders and args are always passed together to the read-only query interface.

Column capabilities are maintained per engine family as allow-lists (`comparison`, `grouping`, `countDistinct`, `regex`, `length`, `extrema`, `text`, plus `noColumnCount` and `noNullTest` exceptions): a type not listed has zero capability and is rejected at save time rather than guessed at run time. `ColumnKind` alone only decides how a literal binds and is not enough. Profile facts use the same table, so profiles and rule validation cannot drift. Notable consequences: arrays cannot bind scalar values, MSSQL `text/ntext/image` cannot be counted/compared/lengthed, binary types show extrema and top values as `0x…`, and PostgreSQL user-defined types keep a deliberately conservative historical allowance.

Judgment (`Evaluate`) uses strict threshold comparison — equal to a bound passes. Empty data is decided by `on_empty ∈ {NOT_EVALUATED (default), PASS, FAIL}`, written into the threshold snapshot on the execution. Freshness lag is computed in SQL with the database clock. `row_count_change` compares against the latest `COMPLETED` execution of the *current* target with `total_rows > 0` inside a recency window (≤7 days and ≤2× the target cadence; zero-row runs are skipped and an expired candidate means no baseline); baseline value and time are stored on the execution. `aggregate` observes one aggregate (percentile only on PostgreSQL and MSSQL; `COUNT` is rejected because it duplicates `row_count`); `group_check` counts groups; `segment_check` compares the current segment set against recent baseline runs (see below); `cross_table` compares a left aggregate with a right one over a registry target reference and judges `max(0, |diff| − tolerance)`; `cel_expression` evaluates the expression in Go over a bounded sample; `custom_sql` wraps the user's single `SELECT`/`WITH` in `SELECT COUNT(*)` for judgment and `SELECT *` for samples and never rewrites it; `schema_drift` compares registry columns with the saved snapshot (missing columns, type/nullability when recorded, order when requested, extra columns when not allowed) and touches no database; `standard_code` validates text rows offline in Go.

PERCENT thresholds are allowed for 12 row/unit types (`unique`, `unique_combination`, `accepted_values`, `range`, `regex`, `string_length`, `referential_integrity`, `cross_column`, `group_check`, `segment_check`, `cel_expression`, `standard_code`). `null_percent` never reads the shared metric — its own config picks count or percentage. Object types: tables and external tables accept every type; views and materialized views accept only table-level rules (`row_count`, `row_count_change`, `freshness`, `custom_sql`, `schema_drift`).

Failure samples are the failing rows themselves: for column rules, the target's primary-key columns first (from registry index metadata, normalized for the engine's quoting form), then the checked column, so several failing rows on one column are distinguishable. Group rules sample the group key, referential rules all child columns, `standard_code` primary key plus checked column. `SQL NULL` and empty string are stored distinctly (`is_null` plus `value`); rows written before that field existed are "unknown". Values are truncated to 256 bytes, samples default to 20 rows (hard ceiling 100), a query result is capped at 1 MiB and stored SQL at 8 KiB; every over-limit case is flagged `truncated`, never treated as a failure. If the primary-key column makes the sample query fail (stale metadata, missing column grant), the sample falls back to the checked column once, except on timeout.

### Execution model

The runner (`backend/runner/qualityrunner`) is a 10s tick over one shared state machine. Constants that matter:

| Constant | Value | Meaning |
| --- | --- | --- |
| Due scan budget | ≤200 rules and ≤50 targets per tick | whole targets only; a target's rules are never cut by the budget |
| Batch cap | ≤100 executions per batch | matches the per-table rule cap, so every legal target fits one batch |
| Scheduled concurrency | 2 instances at once, batches of one instance serial | process-local |
| Retry budget | 3 attempts per check per target cycle (initial + 2) | timeouts/abandons retry on later ticks |
| Scheduled admission wait | 2 minutes | then the batch is not created and its rules stay due |
| Manual admission wait | 5 minutes | then the planned executions and batch are abandoned |
| Manual queue | 512 batches | the API checks capacity before planning anything |
| Batch timeout | 15 minutes | covers every execution and query in the batch |
| Per-check query timeout | config `timeout_seconds` (1–300, default 60) per query | batch deadline remains the hard upper bound |
| Startup sweep | executions/batches older than 15 minutes → ABANDONED | scheduled retries; manual does not |
| Storm threshold | >10 `FAIL` executions in one batch | one summary notification instead of per-issue messages |
| Daily execution limit | setting, default 10,000, UTC day | hitting it only skips the scheduled due scan; manual still runs |

Scheduled path: due targets are those with `next_run_at <= now` and at least one enabled check; the store returns whole targets in first-due order within the budget, each with the checks not yet completed in its cycle (abandoned attempts come back with their next attempt number). One batch per target is created with target identity, path snapshot and one `PENDING` execution per check (revision, target snapshot, instance, trigger, attempt, `started_at`, `scheduled_at` = the target's due slot). Planning does not advance the schedule: the target cycle settles when no planned execution is pending, and the next run is then computed from the stored cadence. A target with more than 100 checks is sharded across batches inside the same cycle; a timed-out or abandoned check retries on a later tick until the attempt budget is spent, then the cycle settles. Per instance, targets run in first-due order and serially; a failed admission skips that instance's remaining targets for the tick (they stay due). The scan only plans and hands instance groups to two scheduled workers, so a long scheduled pass never blocks the manual channel.

Manual path: the API resolves the selection (rules, instance or target), splits it per `(instance, target)`, creates one batch per target and plans its `PENDING` executions (trigger manual, initiator, definition from the head revision, no `scheduled_at`), then enqueues exactly those execution ids. The runner executes those rows and never expands a selection; a full queue abandons the batch and its executions and returns `ResourceExhausted`.

Per execution: batch to `RUNNING` → inflight dedupe (a duplicate trigger becomes `SKIPPED`) → load the latest revision snapshot → resolve the target (orphaned → `SKIPPED(ORPHANED)`) → `RequireTarget`/`ValidateConfig` (unsatisfied → `ERROR(UNSUPPORTED)`) → metadata rules skip the connection, query rules open the target's read-only source under the batch's instance lease → `Executor.Execute` → `row_count_change` baseline lookup → `Evaluate` → write the terminal row (status, observation, thresholds, row counts, sample, SQL, error, duration). Each execution is its own commit point. A panicking execution becomes `ERROR(EXECUTION)` and the rest continue.

If a terminal write fails, the batch times out, or any task cannot produce a committed verdict, the rest of the batch is abandoned and the batch ends `ABANDONED` — a partial rollup is never marked `COMPLETED`. Verdicts already committed still migrate issues and send their per-issue notifications, but no storm summary is sent. The instance lease is released as soon as the query phase ends; issue transition and notification follow best-effort, then batch counts and completion. SQL and sample values are never logged.

The read-only channel is `db.ReadOnlyQueryer`. PostgreSQL gets `SET LOCAL statement_timeout` in a transaction, MySQL gets `MAX_EXECUTION_TIME` and resets it (deliberately one second after the client deadline, so timeouts are attributed to the client); other engines rely on the read-only account and a statement allow-list. Error codes written on the execution: `CONNECTION`, `AUTH`, `TIMEOUT`, `PERMISSION`, `UNSUPPORTED`, `SQL_SYNTAX`, `BAD_DATA`, `LIMIT_EXCEEDED`, `ORPHANED`, `NO_READ_ONLY_SOURCE`, `EXECUTION` (unclassified driver error, message redacted and truncated; `QUOTA` is a historical value that the runner no longer produces).

### Issues, notifications and mute

An issue row carries its target, rule, severity copy, first/last-seen execution and time, occurrence count, resolution reason/note, acknowledgement, and `muted_until`. Notification details carry identifiers, kinds, from/to status, observed value and unit, execution, failed/total rows and error code — never bodies or sample values; detail text is bounded because the notification table is kept forever. Recipients: issue opened/recovered go to the rule owner, falling back to workspace administrators; execution-failed and storm summaries go to administrators; structure-change notifications go to the owners of the target's non-archived checks (all owners when some exist, administrators when every owner is missing, nobody when there are no checks). Dedupe is a 1h window per event key; storm summaries use the internal batch as the key, so exactly one per batch. Muting a rule or issue suppresses only issue opened/recovered messages; execution failures are never muted. A storm suppresses per-issue messages only: issues are still created and recoveries are still announced.

Outbound notification channels are a separate delivery path: five kinds — generic `WEBHOOK`, `DINGTALK`, `WECOM`, `FEISHU`, `EMAIL`. Delivery is asynchronous with retries and never changes inbox semantics; channel configuration, quiet hours and routing live in [notifications.md](notifications.md). Notification failures are logged and do not change execution or issue state.

### The three LLM analyses

The total switch is `enable_llm_analysis` (off by default): when it is off the rule engine is fully functional and every LLM entry point reports `FailedPrecondition`.

| Capability | Entry point | Prompt version | What it produces |
| --- | --- | --- | --- |
| Rule drafts (L1) | `SuggestQualityRule` (synchronous, one target; the agent's triage tool calls the same suggester in-process) | `dq.rule_draft.v1` | 1–5 validated drafts → reconciled into `PENDING` rule-draft suggestions |
| Failure explanation (L2) | `ExplainQualityExecution` (server streaming) | `dq.explain.v1` | hypotheses, evidence, next step → cached and replayed |
| Semantic labels (L3) | `SuggestColumnLabels` | `dq.column_label.v2` | label suggestions plus deterministically mapped rule drafts, both `PENDING` |

A fourth generator is deterministic and model-free: `RecommendQualityChecks` builds rule drafts from cached profiles, existing labels and key metadata (`dq.recommend.v1`), and consumes no LLM quota. It never connects to the target database either. All four paths write into the same suggestion queue and are reconciled by suggestion identity (see below); none creates, enables or runs a rule, and none writes a label except by a human decision that writes it.

Quotas are process-local and reset at 00:00 UTC. L1+L2 share a daily bucket (default 10,000, ceiling 1,000,000); L3 has its own daily column bucket (default 50); concurrency (default 8, max 64) is shared by both. Waiters that are canceled consume neither budget nor slot, settings changes apply to the next analysis, and `GetQualityLLMUsage` reports usage/limits/inflight and the reset time. A restart resets counters to zero.

Output budget comes from the provider profile: default 32,768 tokens, explicit range 256–131,072. A provider 400/422 (for example a `max_tokens` ceiling) is retried once at 4,096; `finish_reason=length` is classified `TRUNCATED`, the draft is discarded and the user is told to narrow the request — there is no automatic retry. Every call gets a correlation id. Failures persist a structured diagnostic (classification code, provider/model, prompt version, output budget, finish reason, token usage, prompt size, provider status, correlation id) without prompt or response bodies; raw bodies are captured only when `RuntimeDebug` is open, into `llm_debug_log` with 7-day retention. Both the diagnostic and the WARN log carry the same correlation id. Structured output is `temperature=0` + JSON mode with strict decoding (code fences stripped, unknown fields rejected, no multi-document/empty/null); parsing failures are not cached. The L1 vocabulary is a closed set of 12 v1 rule types — `custom_sql`, CEL, v1.1 and later types cannot be proposed by the model — and each draft is still filtered by column existence, column scope and rule validation.

Context is data, not instructions: only metadata, DDL, comments, rule definitions, history summaries, lineage and profile summaries are sent, sample rows are never sent by any path (`send_sample_values_to_llm` gates profile extremes and frequent values in the agent's triage context; the three analyses ignore it), embedded `</` sequences are neutralized, and the model has no tools and no database connection. Identical in-flight analyses (same feature, prompt version, provider/model, output budget and prompts) are consolidated into one model call and shared; a canceled leader does not poison surviving followers.

### API, permissions and audit

`DataQualityService` (`proto/v1/v1/data_quality_service.proto`) has 77 RPCs: rule CRUD/preview/run, batch create and batch update, template and code-table CRUD, executions, issues, profiles and labels, suggestions and batch decisions, the three LLM entries, deterministic recommendation, overview, target directory and workspace, read-only runs, target schedule, contract settings/publish/revisions, trend, exports and the HTML report, structure-change acknowledgement, impact and consumption coverage, plan projections, LLM usage, and the agent surface (create/get/list/update/start/pause/disable, adoption settings, conversation, reports, attentions, work-session get/list/messages and resume).

Target directory reads (`ListQualityTargets`) aggregate per target: rule counts, distinct covered fields, open issues, pending drafts and labels, worst recent status (ERROR > FAIL > WARN > PASS > NOT_EVALUATED > SKIPPED > never run), last run time, score and recent pass rate, `schema_changed`, `orphaned`. It supports GUID-prefix filters, path/GUID search, status/issue/draft filters, sorting and offset pagination (page ceiling 1,000). A `targets` exact selection (≤200 keys, deduped, four monitorable object types, request order, pagination ignored) serves the asset pages; a target with no non-archived rule is simply absent, and a target whose checks are all paused is present with zero enabled rules. `GetQualityTarget` adds rules with their latest result, open issues, the same summary, the last 20 completed executions per rule and the target's column list. `GetQualityOverview` computes coverage, score and breakdowns plus 24h counts; only `COMPLETED` executions enter trends.

The permission catalog is `metaxisdata.dataQuality.*` with 28 entries (rules, executions, issues, explain, suggest, profile, labels, contracts, plans, agents, templates, code tables). The member baseline covers the read-only subset plus `explain`, templates/code-table listing and agent get/list; everything else is administrator or custom role. Data-quality settings reuse `settings.get/update`. Read paths that aggregate counts need only `rules.list`.

Audit is per call (`audit=true`): writes, decisions, bulk operations, previews, profile/label writes, LLM calls, recommendation, contract updates and publication, structure acknowledgement, agent management, session resume, and the four bulk egress endpoints (three CSV exports and the report). Plain list/detail/trend reads and scheduled executions are not audited. Audit rows carry request metadata only; exports record the filter and exported row count, the report records the request and file name, and the report body field is redacted by name. Every audited RPC also enters the principal rate budget described in [rate-limiting.md](rate-limiting.md).

### Frontend and i18n

Routes: `/data-quality` (overview), `/data-quality/targets` (target directory), `/data-quality/targets/:targetGuid+` (target workspace, query `metaType`, optional `check` for the check drawer and `highlight`), `/data-quality/checks` (cross-target check directory, read-only plus bulk edit), `/data-quality/issues`, `/data-quality/executions`, `/data-quality/suggestions`, `/data-quality/agents` (agent list), `/data-quality/agents/:workspace/:agentId` (conversation, reports, attention, adoption, recent work sessions), `/data-quality/agents/:workspace/:agentId/sessions` (work-session list, owner/admin) and `/data-quality/agents/:workspace/:agentId/sessions/:sessionId` (full transcript, owner/admin). The old `/data-quality/agents/{workspace}/{id}/diagnostics` URL redirects to the session list. Settings pages are Data Quality and Quality agents. Legacy `/rules` URLs redirect through `RedirectQualityRulePage` to the owning target workspace.

Creating or editing a check happens only in the target workspace through `TargetRuleComposer`, reached from the workspace header, a table/column section, the coverage card or an AI draft. The directory exists for auditing, search and bulk governance; it offers no create and no single edit. Check details are a drawer inside the workspace, not a page. The data-quality tab on a metadata asset shows a contract preview plus labels/profiles and links to the workspace. Page headers show score, pass rate, structure-change badge with an acknowledge action, and the schedule.

Product vocabulary in the UI is "check", while the entity, API and tables remain `QualityRule` / `quality_rule` — a product-naming layer, not a schema change. i18n keys live under `dataQuality.*`, `dataQualitySettings.*`, `menu.dataQuality*` and `notifications.dataQuality*`, dynamic status/trigger keys are registered, and terms are kept in the Data Quality category of `frontend/glossary.json`. New routes must be registered in the layout audit script, `ERROR` and `FAIL` must stay visually and verbally distinct, and saving a check goes through the dry run.

Asset trust signals are a tri-state read of the same target summary: absent from an exact selection means "not monitored", present with zero enabled rules means "all checks paused", present with enabled rules means a real signal (`worstStatus` `UNSPECIFIED` = never run). Unmonitored and paused are always neutral, never green; the signal column is plain text with no nested links.

### Profiles, semantic labels and the suggestion queue

Profiles are deterministic and model-free: one aggregate query per table (row count, nulls, distinct, min/max, length) plus one sample query (`LIMIT 1000`), one `column_profile` row per column. Facts are derived from the same capability table as rule validation: exact distinct when supported, otherwise sample-derived and flagged `distinct_estimated`; min/max only where supported; binary families displayed as `0x…`; top values for low-cardinality columns only; values truncated to 64 bytes and at most 20. A profile run is capped by the workspace column setting, 120 seconds and 4 MiB, and opens the target's source only through the instance connection budget.

Semantic labels live in `column_semantic_label`, unique per `(table_guid, table_type, column_name)`, drawn from a closed enum, with source manual or LLM. Manual writes overwrite; LLM output never overwrites a label. Labeling a column as a resident ID card marks it personal data: profiles are redacted before storage (min/max replaced, top values cleared), execution failure samples are masked before storage for every rule type, and clearing the label does not restore historical redacted values.

The suggestion queue is a reconciliation, not an append log. Each suggestion has a deterministic identity — `label|<column>` or `rule|<type>|<sorted columns>|<discriminator>` — and a partial unique index on `(target_guid, target_type, signature)` where pending allows at most one `PENDING` row per identity. A generation pass creates missing identities, refreshes existing pending ones in place (same row id, updated refresh time), closes identities whose fact now exists as `SUPERSEDED`, and skips already-decided identities and identities covered by an existing rule or label. The summary reports created/refreshed/superseded/skipped counts and skipped columns so the UI can tell the truth instead of claiming "queued N". Across passes, a pass only refreshes pending rows from its own source; deterministic recommendation may refresh a label-pass default-parameter draft with observed thresholds, but not the reverse; explicit user intent outranks derived passes; the database upsert with a conditional update is the arbiter.

Creating a rule from a suggestion claims it first: the pending → accepted decision is the atomic claim, and only the winner writes the rule; a failed write reopens the suggestion. Batch create and batch decide accept up to 200 items, validate and apply each independently, return results in request order, and do not stop on the first failure. The directory also supports a batch update of checks (`BatchUpdateQualityRules`, one audit row): severity, dimension, owner, state, `on_empty` and thresholds only, applied per item through the same update pipeline; definition edits honor the per-item revision while head-only fields are last-write-wins.

### Reports, exports and the weekly digest

Exports are read-only outlets, not new entities. Three server-streaming RPCs export executions, issues and targets as CSV with exactly the filter vocabulary of the matching list. Each page is 1,000 rows, `max_rows` defaults to and is capped at 100,000, the first chunk carries a UTF-8 BOM and the header, chunks are 256 KiB, and the final chunk flags truncation (exactly hitting the cap is not truncation). A process streams at most four exports at once; more is `ResourceExhausted`, never queued. Exports are repeated queries, not a snapshot, so concurrent writes may appear in this or the next export. Cells starting with `=`, `+`, `-`, `@`, TAB or CR are prefixed with a quote to block formula injection. CSV never contains failure samples. Each export writes one audit row with the request filter and exported row count because bulk egress is deliberately audited.

The single-target HTML report is one unary RPC returning a self-contained document: inline CSS/SVG, print styles, zh-CN/en-US prose from Go constants, no external resources. It defaults to 30 days and caps at 90, includes up to 20 failed checks × 5 sample rows, and caps the whole document at 2 MiB with explicit cropping notes when it shrinks. It is the only export that contains source data samples and its footer must warn that forwarding the file forwards the rows; the audit row keeps the request and file name and the body field is redacted by name.

The weekly digest is an outbound event, not an inbox message. `qualitydigestrunner` ticks every 60s; settings hold enabled, weekday, `HH:MM` and IANA time zone (off by default, default Monday 09:00 UTC). It sends the rolling 7-day window ending at the most recent scheduled slot when that slot is at most 24h old, keyed by the ISO week of the slot and recorded in `quality_digest_send` so one period is processed once; a missed window older than 24h is warned about and skipped, not backfilled. Delivery is opt-in: only enabled channels that explicitly subscribe to the digest event receive it — empty event type lists mean "no", routing rules do not select it, and email channels without fixed addresses are skipped. The digest is a workspace-level summary (period, status counts, open/resolved issues, failing checks and targets grouped by owner); owner is a display grouping only. It writes no inbox notification; enqueue failures are retried inside the window and a deterministic event id plus a per-channel unique constraint absorbs duplicate enqueues.

### Declared plan and contract snapshots

Contracts are declarations, not gates: publishing never blocks execution, and a rule save runs normally whether or not the contract was republished. Each target has one `quality_contract` row holding settings (filter, default severity, intent) and a series of explicit `quality_contract_revision` snapshots (settings plus ordered checks with revision, title, type, severity, column and fingerprint). Publishing inside a row lock compares against the latest snapshot; an unchanged fingerprint returns the existing version (`no_changes`), and a changed one records a new immutable version with added/modified/removed counts, a note and the publisher. Snapshot schema versions are never compared across generations; old versions are read with their own comparison rule, so upgrading does not fake "unpublished changes".

Intent is the target's commitment above its checks: criticality, statements (property, column, tolerance as a note), dependents, exemptions (property, column, reason, recorder, expiry), effective date, source, and a reserved domain reference. It is stored in contract settings, so it versions automatically with each publish; exemptions only suppress gaps and never count as covered; expired exemptions stop applying at read time while the snapshot keeps the recorded text. The plan projection derives requirements from a criticality template (IMPORTANT: volume + schema stability; CRITICAL: freshness + volume + uniqueness + schema stability; EXPERIMENTAL: none) unioned with explicit statements, deduplicated by `(property, column)`; a gap is required and not satisfied and not exempted. Satisfied properties come from enabled checks by rule type, column-scoped requirements only from checks on that column. The current plan declaration is a staged coverage list with a base version compared-and-swapped on write; publishing records it and advances the base, an empty declaration returns to pure derivation, cadence is only a read-only projection of the target schedule, and check membership is never copied — live rules remain the only membership truth. Plan coverage is an independent axis from the coverage metric, consumption coverage and quality score; they are shown side by side and must never be converted into one another.

### Quality agent runtime

A quality agent is an internal identity, not an API subject: one `quality_agent` row holds identity and runtime configuration (state, owner, language, database scope, capabilities `suggest`/`adopt`/`patrol`, report schedule, adoption guardrails, budgets) linked to a `SERVICE_ACCOUNT` principal used only as the IAM and audit actor. The principal never appears in the user directory or owner pickers, no token is issued, and there is no external agent write API. The only external surface is the read-only MCP tools. The workspace has a single switch, `agent_runner_enabled`; per-agent state and budgets govern individual agents.

Three runners carry the runtime. `qualityenrollmentrunner` (60s) advances the enrollment queue and scans each in-scope database every 15 minutes against the registry digest; enrollment rows are `PENDING`, `ACTIVE`, `DORMANT`, `OUT_OF_SCOPE`, `GONE`, each agent+target pair one row; scope exit blocks the session as out-of-scope, agent disablement blocks it as agent-disabled, both self-heal when the cause disappears, and an object that disappears from a fully scanned database is marked gone and its session archived. Enrollment creates the only target sessions; there is no product RPC to create, pause, archive or wake one. `qualitysessionrunner` (3s tick) claims due sessions under a lease (15m lease, 10m wake), appends a user message, rebuilds the model input from the transcript after the compacted summary point, and either continues the conversation with the model or runs a deterministic patrol/event review. Compaction is a package constant (around 256k tokens): old tool results are trimmed first, then the oldest tool-pair-balanced region is summarized, the system prompt is never compacted, and transcripts are kept. `qualityagentrunner` (60s) generates each agent's scheduled DAILY/WEEKLY report — scope health, targets and coverage, enabled checks, period verdict counts, new/open issues, pending proposals and a markdown body — aggregated over that agent's enrollment target set rather than a database prefix, idempotent by `(agent_id, period_key)`, and appends a "report ready" message to the conversation.

The agent's toolset is deliberately narrow: scope reads (`get_scope_summary`, `list_scope_targets`, `list_pending_proposals`), target work (`get_target_summary`, `list_recent_executions`, `get_table_context`, `draft_checks`, `block_session`, `schedule_wake`), and memory (`record_asset_fact`, `get_memory`). It has no publish, decide, rule-write or settings tool; every write goes through the in-process tool pipeline, which enforces IAM and writes an audit row. Failure and error executions fan out to every session covering the target, always on, idempotent per execution and capped at 20 events per session per hour.

Each agent also has one owner conversation (`quality-assistant`): the owner sends messages (owner-only, hourly cap), the agent replies, and when no model is available it returns a deterministic scope summary. The owner conversation stays product content only; the per-target work sessions are a separate product read (`GetQualityAgentSession`, `ListQualityAgentSessions`, `ListQualityAgentSessionMessages`) available to the agent's owner and administrators. A work-session transcript shows the wake, the assistant answer, model reasoning when the provider returned it, every tool call with arguments and result, runner notes and compaction checkpoints; the system prompt and runner notes stay folded. These reads follow the un-audited read baseline; only `ResumeQualityAgentSession` remains an administrator-only, audited recovery action. The transcript read starts at the newest page, polls with `after_seq`, and walks older history with `before_seq` (the oldest loaded seq) rather than an offset, so a live append cannot shift the page the reader is walking. Attention items (`BLOCKED`, `PROPOSAL_PENDING`, `REPORT_ANOMALY`) are the owner's to-do list: they send an inbox notification to the owner (administrators when the agent has no owner), a reply restores the target session and resolves the item, and dismiss only closes it. A target-level attention carries the target and its session, so the home list leads with the target, expands inline to up to five pending draft titles, and replies through the same target session; a report anomaly is agent-level and has no target. Proposal-pending attentions created before migration `0065` are backfilled from their `proposal:<target_guid>` dedupe key. Auto-adoption is a guardrailed write: when a triage wake produces drafts and the agent has adopt and suggest capability, adoption mode is not off, the type is in the allow-list, confidence clears the threshold, critical targets are allowed and the daily cap is not spent, the agent creates the check through the normal path as its principal, with the agent's owner as rule owner and `PAUSED` or `ACTIVE` mode deciding the initial state; skipped or failed items stay pending and raise a proposal-pending attention. The adoption ledger is durable and audited. The agent's language is one setting (`en-US`/`zh-CN`, empty follows the owner's profile, then English). It is rendered into every system prompt as a language contract, with a short reminder on each wake because the wake instructions are English; the stored SYSTEM row is updated in place when the language changes, so a long-lived session does not keep the old contract. Server-generated prose (report body, report-ready message, attention text, fallback replies) uses the same `agentlang.ForAgent` decision, so model prose and server prose cannot diverge. Model-written prose is shown as written. Raw transcript internals (system prompt, wake instructions, runner notes and tool names) remain English. Memory holds only confirmed asset facts: agents write them, a fact for the same subject supersedes the older one, and `get_memory` is the only reader.

### Coverage, quality score and recent pass rate

These read models are computed at read time from registry rows and executions; they write nothing, audit nothing and change no judgment. They must never exceed their input boundaries.

Coverage is the share of registry objects that have at least one enabled rule — a static "is anything checking this?" measure, not health. The denominator is the four monitorable object types (table, external table, view, materialized view) under live instances; total columns come from each object's metadata column list because the registry only writes column rows for tables. The numerator is distinct targets with at least one enabled rule that still has a denominator row (registry row present, still one of the four types, instance not soft-deleted); covered columns are the rules' config columns that still exist in the target's current registry column list. Table-level and multi-column rules cover no single column. `judged_table_count` narrows further to targets whose latest completed execution on the same target produced a real verdict. Denominator and column guard are read in one repeatable-read snapshot so numerator and denominator agree. A workspace with no checks can never read 100%; instance and environment breakdowns use the same denominator and sum to the workspace total. Hidden or soft-deleted databases keep their last registry snapshot until the instance sync rewrites it, so their tables can still count.

The quality score is a 0–100 severity-weighted verdict score over judged enabled checks only. Fourteen row/unit types (`null_percent` plus the 13 types whose observation carries row totals) score `clamp(1 − failed_rows/total_rows, 0, 1)` with a fallback to the verdict band when the denominator is not positive; the other six (`row_count`, `row_count_change`, `freshness`, `custom_sql`, `aggregate`, `cross_table`) score PASS=1, WARN=0.5, FAIL=0. `ERROR`, `SKIPPED` and `NOT_EVALUATED` are unscored. Weights are WARNING=1, ERROR=2, CRITICAL=3 (unset counts as WARNING); every target, workspace, dimension and owner score is `100 × Σ(weight×score)/Σweight`, and the workspace is weighted by checks, not an average of target scores. Each participating rule uses its latest completed execution, but only if that execution's target equals the rule's current target — after a target move the rule is unscored until it runs on the new target, and the old target's execution never counts for the new one. When nothing is judged the score is unset (rendered `-`), not 0 or 100. Paused and archived checks never participate, and their history is not retroactively counted.

Recent pass rate (`recent_pass_rate`, `recent_execution_count`) is the PASS/(PASS+WARN+FAIL) share of the target's last 20 completed executions of its currently enabled checks; `WARN` is not a pass, `ERROR`/`SKIPPED`/`NOT_EVALUATED` are excluded, and an execution counts only if its target equals the rule's current target. Score and pass rate are different instruments (per-check weighted latest vs. last-20 by count) and cannot be exchanged. Both appear in the target directory/workspace headers, asset signal cells and the report's target score card; workspace/dimension/owner breakdowns only exist in the overview.

### Structure fingerprint and change acknowledgement

The target's shape is fingerprinted from synced metadata, not by re-reading DDL: ordered columns (name, type, nullability, order) plus the primary key, and for views/materialized views the definition; comments, defaults, charsets, non-primary indexes and statistics are excluded. The fingerprint is stored per metadata row in `meta_registry_schema_fingerprint`, written in the same transaction as the metadata and a strict subset of it, cascaded on delete. The fingerprint algorithm is versioned by a domain constant; changing the algorithm requires bumping the version and rewriting every row. Rule save stores the current fingerprint in `target_meta_hash`; reads compare it with the current fingerprint. A legacy branch relaxes only the "unchanged" direction: a pre-upgrade DDL-hash snapshot that still equals the current DDL hash reads as unchanged, so no false alarms and no migration.

A structure-change notification is emitted only after a sync commits and only for objects whose previous fingerprint existed and now differs — not for backfill, creation, deletion, unmonitored objects or revert. Notifications are deduped per target for one hour, one claim shared by all recipients, and carry no column-level detail. Acknowledging a target updates every non-archived check's `target_meta_hash` to the current fingerprint without writing or bumping a revision and without changing the rule's `updated_by` (the audit ledger records who acknowledged). It is idempotent; a target with no fingerprint returns `FailedPrecondition`. Structure changes never block execution or auto-pause checks, and the signal is "is the current shape still the saved one", not a change log.

### Execution semantics: time variables, sampling, timeout

These live in the rule config outside the config oneof and are part of the immutable revision; zero means the older behavior, and there is no migration. Time variables are a closed whitelist: `${now}`, `${today}`, `${yesterday}`, plus one integer offset on the latter two (`${today-7d}`, `${now-30m}`; units m/h/d, bound 366 days). They are accepted only as the whole value of a filter clause or inside custom SQL text; any other config string containing a token is rejected at save time. Resolution uses the execution's `started_at` (preview uses request time) and the workspace `time_zone`; a local-midnight render becomes a date, otherwise a timestamp. Filter values are bound as typed parameters; custom SQL renders a server-generated literal, so a token inside a comment or string is inert and cannot collide with the user's own placeholders. Saved rules keep the tokens, execution evidence shows the resolved form for custom SQL and placeholders for filters. There is deliberately no `${partition}`: partition windows are filters with variables, and integer partition keys use custom SQL plus a cast.

Sampling is the user's "how much to read" intent and the mechanism belongs to the dialect. `max_rows` is a bounded scan (the filter moves into a derived relation, so the limit counts filtered rows; all engines can express it). `percent` is a native table-sample clause (PostgreSQL `TABLESAMPLE SYSTEM`, MSSQL `TABLESAMPLE ... PERCENT`) and only works on those two engines with table targets; everywhere else it is rejected at save time with a hint to use `max_rows` rather than silently downgraded to a hash predicate (Doris/StarRocks tablet sampling is rejected because missing tablet statistics read the whole table while still being labeled a sample). Ten rule types may sample; row-count, freshness, two-relation rules, `custom_sql`, `schema_drift`, CEL, standard-code and segment checks may not. Sampling is validated at save and again at compile, records `sampled=true` with `sample_rows` equal to the scanned rows (group checks record 0 because their total is a group count), reads failure and passing samples from the same sampled relation, and leaves judgment in sample terms. `max_rows` is an arbitrary prefix, not a random sample; aggregates and evidence are separate statements, each sampled.

`timeout_seconds` (1–300, default 60) applies to each query of a check; the batch's 15-minute deadline remains the hard cap. Save and preview reject out-of-range values, while the runner clamps a stored bad value (0 → default, over the ceiling → ceiling) instead of turning the whole check into `ERROR(UNSUPPORTED)`; timeouts are still classified `ERROR(TIMEOUT)`. The workspace time zone (IANA, default UTC) only affects time variables; it is not used by the digest or retention, and it is the fallback when a cron save leaves the time zone empty (the resolved name is stored on the target, so later workspace changes do not move existing targets).

### Target schedule, frequency tiers and maintenance window

A target schedules either a fixed interval (15 minutes – 7 days) or a five-field cron expression in an IANA time zone, exactly one. Cron validation rejects descriptors (`@daily`), expressions whose adjacent occurrences are closer than 15 minutes, expressions that never fire within five years, and invalid time zones; there is no upper bound on cron spacing. The next run is computed in Go, never by catching up: a late tick schedules only the next occurrence, interval targets schedule `now + interval`. The stored interval column always carries a nominal cadence — the interval itself, or the cron's current nominal spacing clamped to 15 minutes – 7 days — which is the fallback when an expression is cleared and the pacing used by `row_count_change`'s baseline window. Rescheduling computes from now and does not run immediately; a target with no enabled checks keeps its cadence but has no next run; re-enabling or adding a check schedules from the stored cadence. Descriptors, DST edges and corrupt stored rows behave as follows: spring-forward times that do not exist are skipped, fall-back repeats fire once, and a corrupt stored schedule falls back to the nominal interval rather than becoming due every tick.

Each check may declare a frequency tier: unspecified (follows the target, default), hourly, daily or weekly. It is head-only scheduling metadata: it writes no revision, bumps no revision and does not enter the contract fingerprint. The gate compares *target due slots*: a tier passes when no completed scheduled execution of that rule exists with `scheduled_at > next_run_at − tier period`. `scheduled_at` is written when a scheduled execution is planned (the target's due slot) and stays NULL for manual executions. The due-rules read and the pending-count read share one SQL predicate so they cannot drift; a skipped check does not remain pending and the target cycle settles normally. The target tick is a lower bound: a tier equal to the target cadence never skips, a denser tier is a no-op, and a coarser tier runs on the first cycle at least one tier period after the previous slot. There is no per-check cron — a check-specific schedule is expressed by splitting the target.

Data quality has no maintenance-window setting of its own. The workspace quiet hours and one-off maintenance window from Notifications *are* the maintenance window: checks still run, verdicts and inbox messages are still written, and only outbound delivery is deferred until the window ends (channels that bypass quiet hours deliver as usual). It never pauses targets, skips checks or changes judgments.

### Lineage impact, root causes and consumption coverage

Both projections are read-only: no tables, no writes, no audit, no notifications. `GetQualityTargetImpact` walks recorded lineage outward and inward. Downstream assets are breadth-first by layer, default 2 and at most 3 levels, at most 100 nodes and 5 seconds; only the four monitorable object types are reported and other traversed objects count as omitted. Root-cause candidates are upstream within a window (default 24h, at most 168h), at most 50 nodes, ranked by having failing checks, then distance, then evidence recency, at most 20 candidates; evidence is failing rules/executions in the window and structure-fingerprint changes. Truncation is explicit (`depth_reached`, omitted counts) and the walk returns truncation rather than an error on budget exhaustion. "Empty" means the recorded lineage contains no such object — it does not mean there is no consumer, and every surface must say so. The single-target report renders the same assembly, anchored at the latest failing execution in its window, and prints nothing as a root cause when there is no anchor.

Consumption coverage is a second, different denominator: assets that are *read* — objects with at least one outgoing column-lineage edge, excluding self-loops — versus how many of those have at least one enabled check. It is not interchangeable with the coverage metric and must be shown next to it, never converted; an unmonitored consumed asset always counts as a gap.

### Bulk editing the check directory

`BatchUpdateQualityRules` (up to 200 update requests, one audit row, `rules.update`) applies each item through the same pipeline as a single update: update-mask vocabulary, optimistic revision, semantic revalidation that appends a revision, and target schedule synchronization. It is non-atomic and returns per-item name/rule/error in request order. The UI exposes six fields — severity, dimension, owner, state, `on_empty`, thresholds — starts with no field selected, prefills from uniform values, and requires an explicit value when the selection is mixed so a stray click cannot reset a batch. `on_empty` is skipped for the three types where it has no meaning; thresholds are available only when all selected rules share a rule type in the threshold family and carry the same metric, a blank warn value keeps each rule's existing value, an explicit clear removes it, and the client mirrors the server threshold validation. Definition edits on a stale revision fail per item (`Aborted`); head-only fields are last-write-wins. Archive checks are not selectable; the directory still creates nothing, does not bulk-delete and does not bulk-run.

### Standard-code checks, semantic derivation and built-in templates

`standard_code` validates one text column against a standard entirely in Go: unified social credit code, organization code, resident ID card, administrative division, industry classification, or a workspace code table (membership only). The five built-in standards use embedded, offline data — the GB/T 2260 administrative-division table and the GB/T 4754-2017 industry-classification table — plus checksum algorithms: USCC with the MOD 31 check digit, organization code with MOD 11 (`10 → X`, `11 → 0`), resident ID card with MOD 11 plus a real Gregorian birthday and a province prefix (the full historical division table is deliberately not consulted). Values are uppercased and right-trimmed before validation; leading whitespace is a violation. The SQL only selects the primary-key columns and the checked column up to the sample size (default 10,000, at most 100,000), and sampling is its own (`sample_rows`, not the shared sampling setting), with `sampled` propagated to results, trends and the report because a sample is never a full-table conclusion. Views and materialized views are not supported, and the type works on MSSQL because it needs no regex. Resident-ID failure samples are masked before storage (first 6 and last 4 characters kept, the middle replaced by `*`), and labeling a column as a resident ID card extends that masking to every check type on that column. The embedded code tables are a build-time snapshot: updating them means refetching data and running the data sanity tests, and older codes stay accepted as legitimate history. The derivation path maps these labels to standards in code, produces a default `standard_code` draft for label suggestions, and raises PENDING candidates in the deterministic recommendation pass; the label prompt vocabulary was versioned up when these labels were added. Built-in templates are a frontend-only read-only catalog of eight prefill entries (five standards plus primary-key uniqueness, timestamp freshness and email format); applying one only fills the form, and templates are never entities. A natural-language L1 draft cannot name `standard_code` — the model's rule vocabulary is fixed.

### Custom rule templates and workspace code tables

A rule template is a workspace resource: check type plus target-independent parameters plus title, description, severity and dimension. Saving clears every target-bound field — checked columns, referenced parent/child tables and columns, time column, CEL column list, all-columns mode, filter, schema-drift snapshot — and validates the config with a target-independent validator; `schema_drift` and `custom_sql` are rejected because both bind a concrete table, and the rule type cannot change. Templates have no revision or history: updates are last-write-wins, deletes are hard, and existing checks are unaffected. Applying a template only prefills the editor; the save path is still the only way a check exists. The built-in read-only templates and the workspace templates appear side by side in the same Templates area.

A code table is a workspace resource holding a bounded, normalized value list (trimmed, deduplicated, sorted; at most 5,000 values, each at most 256 bytes). Listing returns summaries with value counts; reading one returns the values. Values import line-by-line or from CSV. A code table stores codes only — no code-to-name mapping, no per-row history — and is replaced as a whole on update. A `standard_code` config can reference a code table: for a custom table the check is membership only; for a built-in standard the result is "algorithm passes AND member of the table", letting an operator narrow or replace the embedded snapshot. References are resolved and normalized when a rule, preview or template is saved; a missing or empty table is rejected at save, an unreadable referenced table at run time is `ERROR(UNSUPPORTED)` rather than "everything fails", and deleting a table that a live rule or template references is `FailedPrecondition`.

### Dynamic accepted values, passing-row evidence and segment checks

`accepted_values` has exactly one source: a fixed list, another column of the same target, or a query. The fixed list is a stored constant; the two dynamic sources are target-bound and are cleared from templates — templates carry fixed lists only. Both dynamic sources compile to a `NOT NULL`-filtered subquery (a NULL in the set would make `NOT IN` unknown for every row and silently pass the table), and rule/contract filters constrain only the checked rows, never the reference set. The column source must be another comparable column of the same target. The query source reuses custom-SQL validation (one read-only `SELECT`/`WITH`, at most 8 KiB), time variables and the target's read-only connection, and the server reads only the named value column — extra columns are ignored. Cross-database reach follows the engine (MySQL family and SQL Server can read another database on the same instance through a qualified name; PostgreSQL reads only the target's database), and no engine can reach another instance; cross-instance reconciliation is `cross_table`. On SQL Server the query must be a plain select (no CTE, no top-level `ORDER BY`) because it becomes a derived table, and that is rejected at save. The value column's type and name cannot be validated statically — preview or the first execution is where it surfaces — and the set is re-read on every execution, so aggregate, failure-sample and passing-row statements may see slightly different reference data (judgment follows the aggregate). An empty set makes every non-NULL checked value fail the whole table while preview's `LIMIT 0` probe does not execute the subquery, so the author is responsible for guarding emptiness.

Passing-row evidence is a comparison aid, never a judgment input: when a verdict is WARN or FAIL and the type can express a "passing row" predicate, the same execution keeps a bounded sample of passing rows next to the failure sample. Nine types qualify: the single-relation row rules whose failure predicate can be negated, `referential_integrity` (an `EXISTS` form, so a NULL child value counts as passing when nulls are allowed), and `standard_code`/`cel_expression` which reuse the in-memory sample without a second query. Measurement types, `unique`/`unique_combination`/`group_check` and `custom_sql` have no passing-row form. Bounds, per-value size limit and personal-data redaction match the failure sample; rows whose predicate is unknown (a NULL in the comparison) are neither failed nor passed and appear in neither sample; the sample is only taken when failure samples are enabled, is cleared for other verdicts, and a failed passing-row query only loses the comparison. The HTML report does not read it.

`segment_check` tracks dimension values that quietly disappear: it reads the current segment set over 1–5 grouping columns and compares it with the expectation derived from the last baseline runs of the *current target and current revision*, where a run counts only if it is completed, carries segment evidence and was not truncated. A segment present in at least `min_occurrences` baseline runs (default 2, capped by the available runs) is expected; each expected segment missing now is a failure (`failed_rows` = missing count, `total_rows` = expected count, percentage mode uses the same denominator); a new segment is evidence only. There is no comparison on a first run, without a usable baseline, when the observation is truncated, or when the baseline yields an empty expectation — all of those follow `on_empty` (default `NOT_EVALUATED`). Evidence stores observed segments (at most 500, by row count), new segments, disappeared expected segments (which may exceed 500), truncation, baseline run count and expected count; displayed values are truncated to 128 bytes while segment identity is compared by full-value digest, and personal-data columns are masked. Sampling, views/materialized views and templates reject the type. If personal-data labels cannot be read, the execution fails as `ERROR(EXECUTION)` instead of storing unmasked evidence.

## Configuration pointers

The authoritative definition of rule config is `proto/store/store/data_quality.proto` (`QualityRuleConfig`: one arm per rule type, with `threshold_metric`, `filter`, `on_empty`, `timeout_seconds` and `sampling` outside the oneof); the API mirror lives in `proto/v1/v1/data_quality_service.proto`, and conversion is `backend/api/v1/data_quality_convert.go`. The workspace setting is `DataQualitySetting` in `proto/store/store/setting.proto` (mirrored in the v1 setting service), read and written through the ordinary settings RPCs. The schema is `backend/migrator/migration/LATEST.sql` plus the increments under `backend/migrator/migration/`; a schema change is always both files.

Non-obvious invariants of that mapping:

- JSONB columns store `protojson.Marshal` output of the `proto` store message named in the column SQL comment; read with `common.ProtojsonUnmarshaler`. Change the proto and the store together; proto3 zero values are omitted on the wire and must read as "unset", not as an explicit zero.
- Workspace settings use "zero value = default"; for `DataQualitySetting` the message presence distinguishes "not configured" from an explicit `false`. The settings update replaces the whole message, so a client that omits a string field clears it, while omitting `weekly_digest` preserves the stored digest schedule for old clients.
- `frequency_tier` and the target schedule columns (`schedule_cron`, `schedule_timezone`, `next_run_at`) are scheduling metadata, not judgment: no revision, no contract fingerprint. `quality_execution.scheduled_at` is internal and only feeds the frequency gate.
- Retention windows are constants in the maintenance runner, not settings: executions with their batch 90 days, resolved issues 90 days, profiles and LLM cache and debug log 7 days, decided suggestions 90 days.
- Agent runtime tables are the current single-agent shape; there are no external-agent token or configuration tables.

## Invariants — what must not break

| Rule | Why / guard |
| --- | --- |
| Domain semantics stay in `component/dataquality`; API and runner only orchestrate | keeps the domain testable with plain goldens, free of DB and HTTP detail |
| A target's identity is `(registry GUID, meta type)` plus a display-only path snapshot; resolution validates the current registry row, live instance and visible database | `ResolveTarget` and the store read path |
| The rule head and its latest revision always agree; an execution records the revision and engine version it actually ran | update transaction + `quality_rule_test.go` |
| At most one unresolved issue per rule | partial unique index + transition tests |
| One six-way verdict per execution; `ERROR` and `FAIL` are never merged; batch outcome is a worst-rank rollup for diagnosis only | rollup/status tests |
| `on_empty` alone decides no-data semantics, and the decision is written into the threshold snapshot | evaluator tests |
| Query rules run only on a `READ_ONLY` source — never a fallback admin connection — and their SQL is a single `SELECT`/`WITH`; placeholders and args are always passed together | `ReadOnlyQueryer` + validate/compile + execution evidence |
| Results and samples stay within configured caps; over-limit is `truncated`, never a failure | scanner + API conversion tests |
| Notifications follow state transitions only; issue notifications dedupe for 1h; execution failures cannot be muted; a storm suppresses messages but not issues | issue transition table + notification tests |
| A manual batch executes exactly the executions the API planned, never "all enabled rules of the instance"; a scheduled batch plans its rows and its target cycle settles before the schedule advances; inflight dedupe prevents two executions of one rule at once | enqueue by execution id + planning/admission tests |
| Single replica: inflight, quotas, LLM counters, queues and instance slots are process-local; restart retries scheduled checks within the cycle budget and never manual ones | runner tests |

| The execution resource name ends in the `quality_execution` row id; rules/issues/suggestions use non-recyclable ids; the internal batch has no public name | resource-name converters |
| Soft delete preserves revisions, executions and issues; rules are archived, not deleted | archive path + store filters |
| The connection budget is admitted before a batch and held until the query phase ends; contention is never written as a verdict or `ERROR(QUOTA)` | admission governor tests + [instance-connections.md](instance-connections.md) |
| `quality_run` is read-only; there is no `run` write path and no independent runs page; the execution remains the smallest judged unit | run read model + page tests |
| Batch RPCs are non-atomic per item, ordered, and never abort the rest; creating a rule from a suggestion claims the suggestion first and reopens it on write failure | batch handlers + integration concurrency test |
| One pending suggestion per identity; generation reconciles (upsert, supersede, skip) and reports truthful counts; facts supersede pending proposals | partial unique index + upsert statements |
| Identical in-flight model calls are consolidated; a canceled leader does not poison followers; panic is published to followers | analysis-group tests with `-race` |
| Contract filters merge once at compile (rule clauses first, at most 20 total); `custom_sql` is never rewritten; `schema_drift` has no SQL | compile/executor golden tests |
| Contract publication is a snapshot, not a gate; an equal fingerprint creates no version; snapshots are immutable and never compared across schema generations | contract tests + integration |
| Exports stay bounded and audited, reports stay self-contained and their body redacted, digest periods are idempotent via the unique period key plus a deterministic event id | export/report/digest tests |
| Coverage, score and pass rate never exceed their input boundary (eligible enabled rules, current columns, same target, latest completed execution) and are unset rather than fake when there is nothing to judge | `score_test.go` 20-type contract + API tests |
| The structure fingerprint is derived and read-only, shares the metadata row's transaction and lifecycle, and is compared through two equivalent predicates; the legacy-hash branch only relaxes "unchanged"; acknowledgement never bumps a revision | fingerprint/store/API tests |
| Deterministic recommendation is pure and produces only pending drafts whose thresholds name the observation behind them; cross-pass pending priority is explicit (recommendation may refine a profile default, not the reverse) and the database upsert arbitrates | `recommend_test.go` + `SuggestionPassMayRefreshPending` tests |
| The trend is a pure read normalized by the current definition (a type change truncates with `history_restarted`, the band only for the current revision); historical suggestions need at least five judged executions, never write, and only fill the form on explicit click | `trend_test.go` + API and form tests |
| An agent is an internal identity (one row plus an internal principal, no token, no external write API; external consumers get only the eight read-only MCP quality tools), and its sessions are durable: one active session per target, `ENABLED`/`BLOCKED`/`ARCHIVED`, created only by enrollment, readable by the owner and administrators, and resumable only by an administrator | agent/session tests + MCP tool guards |
| Model reasoning is display-only: it is persisted on the assistant transcript row when the provider returns it, never sent back to the provider, and never counted in the model context | loop/engine tests + conversion test |
| The agent language is one config value used by the system prompt, the wake reminder and server prose; a language change updates the stored SYSTEM row in place, and identifiers are never translated | prompt/language tests + agentlang tests + engine test |
| A wake continues the same conversation; the tool whitelist is read/propose/control only — no publish, decide, rule-write or settings tool; failure events are idempotent and capped | engine/context tool tests |

| Templates carry no target (target-bound fields cleared, `schema_drift`/`custom_sql` rejected, no revision history); code tables are bounded, references resolved at save, a referenced table cannot be deleted, and an unreadable reference errors instead of judging everything | template + code-table tests |
| Dynamic accepted-value sources are exactly one and NULL-filtered; rule filters never constrain the reference set; templates carry fixed lists only | accepted-values goldens and validation matrix |

## Failure modes

| Scenario | Behavior |
| --- | --- |
| No `READ_ONLY` source at create, or removed later | creation is rejected (`FailedPrecondition`, message names the configuration entry) and metadata rules need none; a later removal makes runs report `ERROR(NO_READ_ONLY_SOURCE)` with no admin fallback and the next schedule retries |
| Target connection or credentials fail | `ERROR(CONNECTION/AUTH/PERMISSION)` plus an administrator execution-failed notification; next schedule retries |
| Query timeout, or a check timeout meeting the batch deadline | `ERROR(TIMEOUT)` and scheduled retries within the cycle budget (manual does not); the 15m batch cap wins when they collide, unstarted executions are abandoned and no partial verdict is written |
| Result over the cap | truncated, `truncated=true`, verdict still computed |
| Column deleted or changed after save | run time `ERROR(UNSUPPORTED)`; preview would have rejected the save |
| Target/instance deleted or database hidden | `orphaned_reason` on the rule, `SKIPPED(ORPHANED)` at run time, no notification |
| Target has no usable fingerprint yet (upgraded library not synced, or the read failed) | `schema_changed` stays false and acknowledge returns `FailedPrecondition`; a fingerprint read failure fails that database's schema sync and retries while quality reads keep the old signal, and both recover after a successful sync |
| Legacy DDL-hash snapshot, or a change that reverted between syncs | a legacy snapshot reads as unchanged through the compatibility branch until the rule is edited once; a reverted change leaves equal fingerprints and raises no event (the signal is current shape, not a log) |
| Acknowledge with only archived checks | updates zero rows and returns zero; archived checks participate in neither signal nor acknowledgement |
| Same rule triggered concurrently | in-flight dedupe → the later attempt is `SKIPPED` |
| Restart | startup sweep abandons stale `PENDING`/`RUNNING` rows after 15 minutes; scheduled checks retry within the cycle, manual do not |
| A single execution panics | that execution becomes `ERROR(EXECUTION)`, the rest of the batch continues |
| Terminal write fails, batch times out, a task cannot commit a verdict, or the abandon write fails | remaining executions and the batch are `ABANDONED` with no partial rollup; committed issue transitions and per-issue notifications stand (no storm summary), the batch still tries to end `ABANDONED`, and leftover rows wait for the next startup sweep |
| Batch cannot enter `RUNNING` (duplicate dispatch, swept, already terminal) | its executions and the batch are abandoned; its scheduled checks spend an attempt and retry next tick |
| Notification write fails, or a rule/issue is muted | write failures are logged only and state is unaffected; muting suppresses issue opened/recovered but never execution-failed |
| More than ten failures in one batch | per-issue messages suppressed, one storm summary with target/instance/counts; issues still created and recoveries still sent |
| Daily execution limit reached | scheduled due scan skipped, rules stay due until the next day; manual runs unaffected; no ERROR, no notification |
| LLM daily quota or concurrency exhausted | `ResourceExhausted`; canceled waiters consume nothing; limits adjustable in settings |
| Instance connection budget saturated | scheduled: wait ≤2m, then no batch, rules stay due, retry next tick; manual: wait ≤5m, then abandon; never `ERROR(QUOTA)` |
| Manual queue full | the batch and its executions are abandoned (no outcome) and the API returns `ResourceExhausted` |
| LLM disabled or no provider profile | `FailedPrecondition`; the rule engine is fully available |
| LLM parse failure, timeout, quota exhaustion or a truncated finish | the request fails (Internal/FailedPrecondition/ResourceExhausted) with nothing cached and no rule/issue state changed; `finish_reason=length` is classified `TRUNCATED`, the draft is discarded and the message asks to narrow the request (no auto-retry) |
| Provider returns 400/422 for the token limit | one retry at 4,096 tokens; if refused, `PROVIDER_STATUS` and the profile must be lowered |
| Stream interrupted/too large/unexpected finish reason, or debug capture unavailable | `STREAM_INCOMPLETE`/`RESPONSE_TOO_LARGE`/`UNEXPECTED_FINISH_REASON` (user retries); the structured diagnostic is still returned when `RuntimeDebug` is off or its rows expired, and raw bodies are only findable by correlation id in logs |
| Profile request fails, or recommendation has no fresh profiles | the profile request fails with a renderable error while already written rows remain; recommendation returns `FailedPrecondition` pointing at profile generation and the UI fills missing/stale profiles first |
| A recommended candidate is rejected by the rule pipeline | that candidate is dropped with a WARN (generator defect) and the rest continue |
| Suggestion decided or used to create a rule concurrently | the decision/claim loser gets `Aborted`; only the claim winner writes a rule, a failed rule write reopens the suggestion, and at most one rule exists |
| Identical prompts or repeated suggest/recommend clicks | one model call per identical in-flight prompt with a shared result; same-identity pending rows are refreshed, not appended, already-labeled/already-covered identities are skipped or superseded, and the summary reports it honestly |
| Batch item fails, or a suggestion is used with a different target | the failed item carries an error and the rest continue (the batch call succeeds); a target mismatch returns `InvalidArgument`, creates nothing and leaves the suggestion pending |
| Export concurrency saturated, or data changes mid-export | the fifth concurrent export gets `ResourceExhausted`, not a queue; exports are repeated queries, not snapshots, so new rows may appear now or next time and rows are never half-written |
| Export hits `max_rows` | final chunk `truncated=true`; the file is still complete; the UI says only the first N rows were exported |
| Report exceeds its size budget | the renderer shrinks samples/checks/text and states the cropping; the audit row still succeeds |
| Digest has no subscribed channel, or its enqueue fails | no channel means the period is recorded with zero channels and no error; a failed enqueue leaves the period unrecorded so the next tick inside the window retries, and the deterministic event id prevents duplicates |
| Digest missed by more than 24h (downtime) | not backfilled; each crossed period logs one warning, then normal scheduling resumes |
| Multiple replicas | unsupported: executions and LLM quotas duplicate per replica; digest periods remain idempotent because their ledger is table-unique, but process-local counters and warnings diverge |
| Sampling unavailable for the target, or a time variable malformed/misplaced | save/preview `InvalidArgument` (percentage suggests a row limit; misplaced or mixed tokens are rejected); a stored row that bypassed the API is rejected at validate/compile → `ERROR(UNSUPPORTED)`, timeout being the exception (clamped); a token inside a quoted custom-SQL literal fails parsing at save but is inert in a comment or dollar-quoted block |
| Sampled query has no failing rows | `samples` is empty but the verdict stands (it comes from sample counts) |
| Personal-data label read fails during a segment check | `ERROR(EXECUTION)` with a message that labels could not be read; no segment evidence and no verdict |
| Cron is invalid (both/neither form, not five fields, descriptor, less than 15m apart, never fires, bad zone) or hits a DST edge | `InvalidArgument` for the invalid form and the existing schedule is unchanged; nonexistent spring-forward times are skipped that day and repeated fall-back times fire once |
| Downtime with cron, or a corrupt stored schedule | only the next occurrence after now is scheduled and missed occurrences are not backfilled; a corrupt stored expression falls back to the nominal interval, never becomes due every tick, and is repaired by editing the schedule |
| Frequency tier denser than target, or a check skipped by its tier | a denser tier is a no-op; a skip leaves the check non-pending, the cycle still settles and advances, and it runs on the first qualifying cycle |
| Manual run of a tiered check | no slot, not gated, always runs |
| Check fails during the maintenance window | it runs, judgment/inbox writes happen, outbound delivery is deferred |

## Deliberate gaps and trade-offs

| Gap or trade-off | Why / boundary |
| --- | --- |
| Daily execution limit silently skips the scheduled scan | rules stay due and resume the next day; writing a fake quota execution or alerting on it was rejected |
| `send_sample_values_to_llm` only affects the agent's triage context | the three analyses and the explain path never consume it; the agent's `get_table_context` sends profile extremes and frequent values only when it is on, so the switch is a narrower disclosure than "send sample rows" suggests |
| `row_count_change` baseline needs a run within 7 days and 2× the target cadence | a monthly/yearly cron can never establish a baseline; baseline is the latest non-empty completed run regardless of verdict, so a default rule judges from its second run |
| No multi-replica support | two replicas execute twice and keep separate LLM counters; the single-replica assumption is documented in [security-posture.md](../../docs/security-posture.md) |
| No distribution-drift/ML anomaly, no RuleSet-style whole-contract validation, no per-check cron, no connection-wait latency histogram | non-goals and known gaps: schedule granularity is the target with coarser tiers only, and admission/defer/abandon and in-flight metrics exist without a latency histogram |
| Creating a rule from a suggestion has a crash window after the claim | the suggestion can read as accepted with no rule — a legal state, recoverable by editing; the alternative was double rules |
| LLM diagnostics are incomplete at the edges | a truncated call has no token usage (the stream fails before the usage block) while provider, model, stop reason and prompt size remain, and the debug-log `error_code` is best-effort (an asynchronous UPDATE can precede the INSERT); the structured diagnostic is authoritative |
| Suggestions written before the identity scheme are not re-keyed | they carry a legacy signature and are neither auto-closed nor merged; a reviewer decides them or they age out |
| `target_schema_changed` is a boolean without column detail | it only encodes columns/keys/view definition; partition and property changes no longer raise it; it never blocks or pauses anything |
| Exports and the report are bounded single-shot outlets | exports are not snapshots and do not report remaining rows (`truncated` is binary; there is no per-target/per-batch entry point); the report is single-target HTML only with no workspace report, PDF or scheduled subscription, workspace coverage/score have no report outlet, and the six-way pass rate and quality score stay different metrics |
| Digest is a workspace-level summary with opt-in channels only | no per-owner recipients or routing, no backfill beyond 24h, and `include_audience` does not apply |
| Coverage, score and asset signals pay for their inputs | hidden/soft-deleted databases keep tables until a sync rewrites them, only rules with a denominator row and existing columns count, and each overview read scans the registry (a large registry wants a cache or roll-up); the exact signal selection pushes aggregation down per target plus one extra registry column read per page, while the unfiltered directory aggregates the workspace bounded by the 1,000-rule cap |
| Deterministic recommendation is deliberately conservative | thresholds come from one observation and must be human-confirmed; at most 12 candidates with per-type budgets, table-level only for views, no schema-drift/group/cross/CEL/custom-SQL candidates, and primary keys never get a uniqueness check |
| Trend and suggestion boundaries | only judged executions are plotted; editing a filter changes comparability, a type change truncates, `row_count_change` has no band, three types get no suggestion, the window is at most 90 points, and there is no report/MCP digest outlet |
| Sampling limits are honest rather than universal | percentage sampling only on PostgreSQL/MSSQL tables; row limits are prefixes, not random samples; Doris/StarRocks tablet sampling was rejected because missing statistics read everything |
| Time variables deliberately stop at filters and custom SQL | no `${partition}` and no general template language; integer partition keys need custom SQL plus a cast |
| Cross-table reconciliation is aggregate-only | the reference must be a synced registry object; per-row reconciliation is custom SQL; separate connections mean two snapshots (or two statements on one connection); a second connection is non-blocking, so an instance with a concurrency limit of one rejects such rules at save time |
| Dynamic accepted-value queries cannot be statically typed | the value column's type/name and emptiness surface at preview or first execution; the reference set is re-read per statement, so evidence can differ from the aggregate |
| Passing rows and segment evidence are expensive | failure evidence can nearly double, segment evidence shares the sample JSONB and is returned by both list and detail reads, and a check that consistently exceeds 500 segments never evaluates until narrowed; segment baselines are counted in runs, so the 90-day retention can silently remove them, a definition edit reopens them, and a new segment alone is never a failure |
| The whole-message settings update can clear the check time zone | an old client updating another DQ setting resets it to UTC; the digest schedule is the only field that preserves itself when omitted |
| Cron and frequency tiers are scheduling approximations | a cron schedule guarantees "the next occurrence after now", not every planned occurrence (missed slots are not compensated and there is no misfire policy — run manually if needed), and a tier measures target due slots rather than start times or wall-clock intervals: weekly on a daily target means the seventh following cycle, and "Mondays 02:00 only for this check" requires splitting the target |
| There is no data-quality maintenance window | the workspace quiet hours are reused; checks still run and write, only outbound delivery is deferred |
| The MCP quality surface is strictly read-only and does not expose LLM explain | the caller is itself a model and should explain from evidence; no publish/decide/run/rule writes |
| Built-in standard data is a build-time snapshot | standards update only by refreshing data and shipping; revoked codes remain accepted as history; USCC's embedded organization-code digit and ID-card sequence/old-format rules are intentionally not validated to avoid false positives |
| Templates and code tables have no history | templates are last-write-wins and hard-deleted (the built-in layer is read-only and ships with the frontend); code tables store codes only — no names, incremental import or per-value history — and a referenced table that becomes empty errors at run time instead of producing a silent empty verdict |
